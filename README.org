* Build a site from a recipe

Libresite turns a YAML recipe into a website project in a new output directory. A pipeline can define the product, establish its design, implement a frontend, backend and database, review the result, and check required artifacts. Every AI step can use a different provider, model, effort level, timeout and retry limit. The generated project includes its own build/run documentation; libresite does not host, deploy or execute generated code.

The implementation is a reusable GLib/GObject library plus a CLI, with the =config.mk= / =rules.mk= / =Makefile= layout used by ai-glib and clawtilla. Extend it with a native =LsStep= subclass or an alternative =LsProvider= transport. Ten built-in step names cover the common workflows, including a native design =gate=; arbitrary module options and prompt overrides support additional tasks without changing the recipe grammar.

Bundled static recipes start with a native =scaffold= step: a Makefile, 404 page, privacy/terms draft shells, contact-form contract and =AGENTS.md= are emitted without a model call. Existing seed artifacts win; subsequent model steps focus on design and integration. See [[file:docs/scaffold.org][native scaffolding]] for the exact files, preview behavior and static-only scope.

Mobile and desktop are first-class generation defaults for every site, application and design profile; no recipe flag is needed. The shared prompts require deliberate layouts and complete workflows on phones, tablets and desktops, with responsive acceptance steps in the generated documentation and =AGENTS.md=. These are generation requirements, not a claim of verified browser rendering; see [[file:docs/prompts.org::*Mobile and desktop defaults][the responsive contract and verification limits]].

Accessibility and conforming WAI-ARIA 1.2 usage are also generation defaults across every route and state. The catalog requires native HTML semantics, correct names/roles/states, keyboard and focus behavior, and generated automated browser audits plus manual screen-reader procedures. Libresite does not execute generated code or certify conformance: see [[file:docs/prompts.org::*Accessibility and ARIA defaults][the accessibility contract and verification limits]].

Generated sites use open-source fonts from Bunny Fonts by default, with system fallback stacks for offline or blocked requests. Explicit font families, sources and hosting requirements take precedence; no recipe flag is needed. See [[file:docs/prompts.org::*Font defaults][font defaults and overrides]].

Search-engine optimization is also a generation default: public-route metadata, canonical URLs, structured data, social cards, sitemap/robots handling and project SEO tests. Generated projects include maintained SEO configuration and a guide; sites without a supplied production URL remain usable noindex previews, and private applications keep their data out of sitemaps. Static projects include a local production-preparation command. See [[file:docs/seo.org][SEO defaults, deployment modes and verification limits]].

* Getting started

The bundled recipes use =timeout: 0= and =max_tokens: 0= for unlimited testing. =--unlimited= also disables both budgets for an existing recipe without changing its checkpoint identity. =--timeout 0= disables only the deadline. Provider/model limits still apply. The flagship recipe has no advisory generated-file byte budgets.

** Build requirements

Fedora packages for the builder: =gcc=, =make=, =pkgconf-pkg-config=, =glib2-devel=, =json-glib-devel=, =libsoup3-devel=, =libyaml-devel=, =libxml2-devel= and =libdex-devel=. Testing also uses =ShellCheck=, =ripgrep= and =coreutils=. The default builds the pinned dependencies from =deps/=; a recursive submodule checkout is the documented first step, and =bundled-deps= initializes missing nested ai-glib gitlinks if you skip it. Alternatively, =DEPS=system= uses compatible installed =ai-glib-1.0= and =yaml-glib-1.0= development builds. See [[file:docs/building.org][building.org]] for details.

On Immutablue/Hyacinth Macaw add missing packages to the image build. No host package installation or writable-/usr overlay is part of this project.

#+begin_src bash
git submodule update --init --recursive
make -j4
make tests
./build/release/libresite --help
./build/release/libresite -r recipes/landing.yaml --validate
./build/release/libresite -r recipes/landing.yaml --plan
./build/release/libresite -r recipes/landing.yaml --preview design
./build/release/libresite -r recipes/landing.yaml --preview design-gate
./build/release/libresite -r recipes/landing.yaml -o ./my-site
./build/release/libresite -r recipes/landing.yaml -o ./my-site --resume --approve design-gate
./build/release/libresite --qa ./my-site
#+end_src

Generation requires Git (Fedora =git-core=) and an installed and authenticated CLI for the chosen provider: =codex=, =claude=, =grok=, =cursor-agent= or =agy=. Libresite uses ai-glib's adapters and provider-native defaults; it does not store API credentials. AI generation uses your provider account. The offline test suite does not make real model calls.

The requested output directory contains a standalone Git repository on =master= with the initial Conventional Commit =chore: initial generated project=. Generated =.gitignore= rules are preserved and extended with defaults for local metadata, secrets, build output, caches and databases; source files, dependency lockfiles and environment examples remain eligible for tracking. The automated commit is attributed to =Libresite <libresite@localhost>= without changing your Git configuration. No remote is created and nothing is pushed. See [[file:docs/operations.org][operations.org]] for publication and recovery details.

Open a generated static =index.html= directly, or follow the output's =README.org= and =AGENTS.md= for application build/run instructions. A loopback application must work from both =http://127.0.0.1:PORT/= and =http://localhost:PORT/=; the database file is created on first start. From cmacs, =M-x compile= can run the builder, and =C-x C-f= opens the output's org documentation or source files.

** Revise an existing project

Use =--revise DIR= with a change recipe whose =site.brief= describes the requested edits. Existing files enter the pipeline as context; omitted files survive and explicit deletions are transactional. The source stays unchanged and the new output receives its own =feat: revise existing project= commit. The input supports regular UTF-8 text, binary assets (PNG, WebP, ICO, fonts) and executable intent; symlinks and special files are rejected. See [[file:docs/revision.org][revision.org]] for input selection, limits and source-bound resume.

#+begin_src bash
./build/release/libresite -r recipes/revision.yaml --revise ./my-site --preview revision
./build/release/libresite -r recipes/revision.yaml --revise ./my-site -o ./my-site-v2
#+end_src


** Supply initial artifacts

To start with client copy, logo SVG, brand YAML, approved legal text or binary assets, add a top-level =seed_artifacts= sequence of =path= / =content= mappings to the recipe. UTF-8 is the default; binary seeds set =encoding: base64=. These files populate previews and the initial checkpoint before any step runs. See [[file:docs/recipe-format.org::*Seed artifacts][seed artifact syntax and resume semantics]].

** Resume interrupted generation

#+begin_src bash
./build/release/libresite -r recipes/landing.yaml -o ./my-site --resume
#+end_src

Successful steps are saved under =my-site.libresite-work/checkpoint.json=. Resume restores their files and starts at the next step. Bundled recipes stop at =design-gate= until you inspect =OUTPUT.libresite-work/review/design-gate/= and resume with =--approve design-gate= (or =--approve-all= for unattended runs). The parsed recipe and exact prompt catalog must match. Existing output directories are never overwritten. The output's parent directory must already exist. Concurrent runs targeting the same workspace are rejected. After publication, =--qa DIR= inspects HTML structure and local asset references without executing generated code; native =validate= remains the in-process literal check.

Stderr reports attempt numbers, per-attempt timeouts, retry reasons and a waiting heartbeat every 30 seconds. Accepted artifacts advance only after successful steps; accounting also updates before execution and on failure; =timeout: 900= with =retries: 1= can spend 30 minutes on one step before failing.

Add =--debug= to enable provider session persistence (including Codex JSONL rollouts) and diagnostic metadata on stderr. The logged provider working directory identifies the session while it runs. Debug can be enabled when resuming an existing checkpoint; see [[file:docs/operations.org][debug tracing]].

For a large response killed by the recipe's deadline, resume with =--timeout 3600= to allow up to an hour per attempt without changing the recipe or checkpoint. The timeout is total elapsed time, not idle time. An unchanged Codex session JSONL does not prove a stall: response tokens can still be arriving before a completed item is recorded. Resolved AI settings, including the output budget, are now included in the model prompt; Codex's adapter does not enforce =max_tokens= as a native CLI limit.

Prompt size is unlimited by default. Use =--max-prompt-bytes BYTES= only when you want a local cap; =0= disables it. Runs stopped by the former 100000-byte limit can resume with the rebuilt binary and their original recipe/catalog. Provider token windows still apply. Changing this CLI cap does not invalidate a checkpoint.

** Choose a recipe

The [[file:docs/packages.org][sold package catalog]] provides =trades=, =professional-services=, =restaurant=, =nonprofit=, =studio= and =small-saas= vertical site SKUs, plus the =c-glib= application SKU. Each has a fixed page/workflow scope and native acceptance predicates. Flagship quality is the shared catalog default; =landing.yaml= now delivers the complete studio package. Small SaaS marketing and working application implementation are separate scopes.

Before generating a sold order, seal its approved recipe and exact selected catalog. The archive carries SKU release metadata and SHA-256 pins, so future resume does not depend on the catalog installed that year:

#+begin_src bash
./build/release/libresite -r recipes/trades.yaml --seal-package ./order-2026-001
./build/release/libresite --package ./order-2026-001 -o ./client-site
./build/release/libresite --package ./order-2026-001 -o ./client-site --resume
#+end_src

Replace illustrative business facts with approved client inputs before sealing a real sale. Archive the package and checkpoint together; preserve compatible generator/plugin versions separately. Sealing pins inputs and scope, not model output or verified visual quality.

For new recipes, fill =site.pages=, =offers=, =contact=, =brand=, =copy_lock= and =languages= as shown in [[file:recipes/structured.yaml][structured.yaml]]. A platform can submit those fields with =libresite --from-form form.json > site.yaml= or use the library form/serialization API; see [[file:docs/structured-recipes.org][structured recipes and form integration]]. Legacy =site.brief= recipes remain supported. Choose the requested stack and design profile: =editorial=, =minimalist=, =industrial=, =cinematic= or =application=. Provider model identifiers are passed through to ai-glib; example model aliases are examples, not a promise of account availability.

The application SKU requires =site.stack: c-glib= to supply pinned GitLab dependency setup, verified library API context, YAML runtime configuration, HTMX progressive enhancement, SQLite first-start initialization and optional provider bootstrap SQL. React/Tailwind requests require an explicitly selected plugin or different generator and a separate scope; they do not add stacks to the supported application SKU. The [[file:docs/c-application.org][C application guide]] explains output artifacts, Fedora packages and verification limits. This stack profile is independent of visual style and does not add ORM/HTTP runtime dependencies to the builder.

** Generate the flagship site

For the fuller example, use a fresh output directory:

#+begin_src bash
./build/release/libresite -r recipes/flagship.yaml --plan
./build/release/libresite -r recipes/flagship.yaml --preview foundation
./build/release/libresite -r recipes/flagship.yaml -o ./fieldwork-site
# Inspect the generated test script before executing generated code.
bash ./fieldwork-site/tests/check.sh
python3 -m http.server 8000 --bind 127.0.0.1 --directory ./fieldwork-site
#+end_src

Visit =http://127.0.0.1:8000=. The [[file:docs/flagship.org][flagship guide]] describes the routes, staged generation, local-only interactions and browser acceptance procedure. This recipe and the default studio SKU make eight AI calls before retries. Prompts specify the shared visual standard; offline tests cannot certify the generated design.

** Edit prompts in one place

[[file:data/prompts.yaml][data/prompts.yaml]] holds the shared system instructions, design profiles and stage contracts. It is embedded with GResource at build time and can be replaced without recompilation:

#+begin_src bash
./build/release/libresite -r recipes/landing.yaml --prompts data/prompts.yaml --preview foundation
#+end_src

The design profiles distill the design skills under =~/.agents/skills/= into consistent, runnable guidance. Snapshots and provenance ship under =data/design-references/= and [[file:docs/prompts.org][prompts.org]]. The installed binary works without the source checkout or a personal skills directory.

** Drive it from an agent

Repository skills live in [[file:skills/libresite-landing/SKILL.md][skills/libresite-landing]] and [[file:skills/libresite-application/SKILL.md][skills/libresite-application]]. They teach agents to turn a concrete brief into a validated recipe, inspect prompts and execute the pipeline. An agent can read these files directly; normal skill installation/discovery is optional.

* Step usage and job pricing

Each executed step records provider, requested model, elapsed microseconds, attempts/retries and input/output bytes in checkpoint and run metadata, including normal failures. Use =libresite --price-usage my-site/.libresite/run.json --rates rates.yaml= to price the structured history offline. See [[file:docs/usage.org][usage records, rate-card format and accounting limits]].
