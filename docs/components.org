* Why it exists

Measured on the eight-page studio recipe, the file-bundle pipeline spent 28 to 37 minutes to ship 69 KB. Almost none of that was writing the site: it went to hidden thinking, resending rejected whole-site bundles, retyping pages in later passes, and eight model calls in a row. Only a quarter of what the model wrote was unique, visitor-facing work.

The component pipeline keeps the model on what is specific to a customer (the design system, the words, the art and the composition) and lets the builder produce the rest deterministically. The same studio recipe now completes in about a minute of model time, with every page and artwork written at the same time. See [[*Measured runs][measured runs]] for current numbers.

* The pipeline

#+begin_src yaml
pipeline:
  steps:
    - {id: plan, type: plan, instructions: ...}
    - {id: pages, type: pages, options: {parallel: 12}, instructions: ...}
    - id: acceptance
      type: validate
      options: {required: [...], checks: [...]}
    - {id: build-notes, type: prune, options: {prefixes: [site/], archive: true}}
#+end_src

1. =plan= makes one model call and stores =site/plan.json=: design tokens, optional web fonts, brand, navigation, footer, voice, the artwork list and every route with a title, meta description and a short brief. Mechanical token misses are repaired natively (see [[*Plan repair][plan repair]]); anything else is rejected with every problem listed, and retried.
2. =pages= reads the plan and writes one page specification per route and one SVG per planned artwork, all at once on worker threads, up to =options.parallel= (1 to 16, default 6) in flight. Each answer is checked on the step thread; a rejected answer is retried alone with its exact rejection. When every job is accepted the builder composes the whole site, runs the immediately following =validate= steps on the candidate, and sends a failure back to the one page that caused it. Nothing reaches the project until the composed site passes.
3. =validate= checks the composed files as with any recipe.
4. =prune= with =prefixes: [site/]= and =archive: true= takes the plan and page specifications out of the published site and keeps them in the run record (=.libresite/run.json=, member =archive=). They are the site's source: editing and theme switching work on them, and the pages are drawn from them.

=pages= with =options.mode: review= is an optional second pass: each writer receives its current specification and returns an improved one. Artwork is kept.

Both steps are AI steps. They use the recipe's =ai= settings and a per-step =ai= override, like generation steps. They need a catalog with =spec_system= and the =plan=, =page=, =art= and =page-review= stages; replacement catalogs without them fail preflight. They generate new sites only; revise an existing project with generation steps.

* Page kinds

Every planned page has a =kind=, defined in =catalog.yaml=. A kind fixes which components may open the page and whether wide screens get an in-page contents column. Only =home= may open with a =hero=, =cover= or =manifesto=; a =hero= or =cover= is rejected anywhere else, so interior pages never open like a landing page.

| Kind | For | Opens with | Contents column |
|------+-----+------------+-----------------|
| home | the front door (always =index.html=) | hero, cover, manifesto or custom | no |
| index | lists: work, articles, services, locations | page-header | no |
| detail | one project, service, dish or product | page-header | yes |
| article | essays, guides, case studies | page-header | yes |
| menu | menus and price lists | page-header | no |
| visit | hours, address, directions | page-header | no |
| about | story, people, milestones | page-header | no |
| form | a page built around one task | page-header | no |
| services | what the business offers | page-header | no |
| pricing | packages and tiers | page-header | no |
| contact | ways to get in touch | page-header | no |
| gallery | a portfolio or photo page | page-header | no |
| events | dated events, places and how to join | page-header | no |
| general | anything else | page-header | no |
| utility | built-in 404, privacy and terms (not plannable) | page-header | no |

=page-header= renders a breadcrumb back home on every interior page. Reading kinds show a sticky contents column built from the page's headed sections and article parts once there are at least two; a page may add an =aside= rich-text note under it. Plan repair sets a missing kind (=home= for =index.html=, else =general=) and moves a misplaced =home= to =general=. The reference each writer receives lists every kind with its openings and suited components.

* Look and overrides

Colors and fonts alone do not make two sites different: the skeleton does. The plan's =look= picks one value for each axis in =catalog.yaml= (=looks=), and the builder puts one class per axis on every page's =body=, for example =look-header-stacked=. =look.css= reshapes every component through those classes.

- header: bar, centered, stacked, inverted, floating, glass (sticky frosted bar)
- nav: underline, pill, caps, slashes
- heads: plain, rule, numbered, bar, split, giant
- buttons: square, pill, underline, offset, glass, hud (cut-corner monospace)
- panels (cards, tiles, boxed items across components): flat, outlined, raised, rules, inverted, glass (frosted translucent, solid without backdrop-filter or with reduced transparency), hud (cut corners, accent brackets, inner glow)
- rhythm: even, bands, divided, tight
- align: left, center
- images: plain, rounded, framed, print, shadow
- footer: simple, big, inverted
- texture: none, grain, grid, dots, lines, aurora (fixed color fields for glass), scanlines, stars
- motion: none, rise (scroll-linked, off for reduced motion)
- emphasis (words marked =*like this*= in section headings): accent, italic, highlight, underline, outline, block
- ornament between sections: none, wave, zigzag, dots, star, rule
- kicker labels: mono, pill, line, accent, number
- backdrop behind the opening section: none, glow, mesh, stripes, halftone, block, aurora, horizon (glowing perspective grid)

Section headings may mark one or two words as =*emphasis*=. The builder renders them as =<em class="em">= inside the heading only; contents entries, breadcrumbs, labels and anchors get the plain text, and unpaired or empty markers stay literal.

Home pages rotate openings: the plan task carries a =suggested_opening= (component/variant among the home openings) that =ls_components_suggest_opening()= hashes from the recipe name and brief, so home pages do not all open with the same hero.

The first value of each axis is the default, and plan repair fills a missing axis with it. An axis may set =plain: N= in the catalog: the builder then deals its default to about N percent of sites. Texture and backdrop use 50, so busy backgrounds stay occasional instead of appearing on every site (=/components/plain-share=). Inverted areas swap the working color tokens locally, so every component inside them keeps its contrast pairs. So that sites do not converge on a favorite set, the plan task carries a =suggested_look= that =ls_components_suggest_look()= derives from a hash of the recipe name and brief: different sites start from different skeletons, and the same site always gets the same suggestion. The plan keeps a suggested value unless the subject argues against it.

Every component can be overridden. =styles.css= declares =@layer ls-base, ls-components, ls-look=; the base stylesheet, each component's styles and the look sit in those layers, and everything a site writes is unlayered after them:

1. =restyle=, a plan map from component name to CSS, is emitted after the look and only for components the site uses. Target =.NAME=, =.NAME--VARIANT= and =.NAME__PART=.
2. The plan's =css= follows, for site-wide signature rules.
3. Page =css= is inlined per page, and every section has an =id=.

Unlayered rules beat layered ones regardless of specificity, so an override never needs =!important= or longer selectors. The reduced-motion rules are layered =!important= declarations and still win. Restyle entries are checked like plan CSS (8 KB each, 24 KB in total).

The model-facing reference lists the axes and the override rules (LOOK and OVERRIDES). =/components/every-look= requires styles for each non-default look value, and checks that the plan schema lists exactly the catalog's axes and values; the schema's kind and look enums are generated from the catalog at load.

* Themes

A theme is a complete design applied to the whole site: every token, the web fonts, one value for every look axis and signature CSS. =data/components/themes.yaml= bundles eighteen: editorial, brutalist, midnight, soft, civic, atelier, workshop, neon, terracotta, nordic, retro, zine, botanical, noir, sunrise, liquid-glass (frosted glass over dawn color fields), orbital (sci-fi mission control: HUD panels, scanlines, a horizon grid) and hologram (glass panels glowing over a violet starfield). Every component draws only on tokens and look classes, so applying a theme changes every component on every page together, while content, routes, navigation, art and component choices stay as they are.

Name one on the plan step:

#+begin_src yaml
- {id: plan, type: plan, options: {theme: midnight}}
#+end_src

The plan call then uses a schema without tokens, fonts, look, css and restyle, and TASK carries the theme's name and summary, so the model writes only content and structure and returns a shorter plan. The builder applies the theme to the answer before repairing and checking it. The plan options are =theme= and =sector= (see [[*Identities][identities]]); an unknown theme or sector fails preflight with the list of choices.

=ls_components_apply_theme()= does the same to any plan: it replaces the design half and leaves the rest. Themes are checked like plans when the library loads (contrast, token ranges, fonts, CSS), so applying one can never produce a plan that fails its own checks, and the library's copy is never edited. To add a theme, add an entry with a summary, all tokens, fonts, every look axis and optional css or restyle; =/components/themes= composes the fixture site under every theme.

Recomposing an already delivered site needs its plan and page specifications. Composed recipes archive them in the run record (see [[*The pipeline][the pipeline]]); a command that recomposes a delivered site from them is not built yet.

* Identities

Without a theme the model designs each site itself, and left alone it converges: five live packages on 2026-09-28 all came back with warm cream paper, a rust accent and Fraunces headlines, and nearly the same home page order. Nothing tied the design to the business. Identities fix that without extra calls.

=data/components/identities.yaml= defines business sectors (trades, food, community, advisory, software, creative, retail and wellness), twenty-one palettes, fifteen type pairings and twelve home-page section sequences, each listing the sectors it fits. Name the sector on the plan step:

#+begin_src yaml
- {id: plan, type: plan, options: {sector: trades}}
#+end_src

The builder deals one fitting palette, type pairing and home sequence from a hash of the recipe name and brief, the same way it deals the look, so one site always gets the same suggestion and sites in one sector spread across the choices. TASK carries them as =suggested_palette= (name, summary, the seven color tokens), =suggested_type= (name, summary, font tokens and Bunny Fonts families) and =suggested_home= (component names after the opening). Without a sector, or for a themed plan's palette and type, every entry is eligible or the theme supplies the design; the home sequence is dealt either way.

The plan starts with =character=: one or two sentences on what the business looks like in the real world (materials, tools, place, era, mood). Its colors and type start from the dealt identity and move toward that character; the model departs from them only when the character needs it. =ls_components_check_identity()= then rejects a plan that falls back on the house default, warm cream paper with a rust or orange accent or Fraunces over Source Sans, unless the dealt identity was itself that warm; the rejection goes back to the model like any other. No palette or type pairing in the catalog may be the default, and each is checked like a plan when the library loads (contrast, fonts, token ranges). =character= is required by the plan schema and optional natively, up to 600 characters.

To add a palette, type pairing or home sequence, add an entry with its =fits=; a sector needs at least one of each. =/components/identities= checks fit, stability and spread; =/pages/plan-identity= checks the prompt and the rejection.

* Photographs

A recipe can supply real photographs, such as the customer's own or licensed stock. Each is a binary seed artifact under =assets/= (=encoding: base64=) listed in =site.photos= with its alt text and an optional credit:

#+begin_src yaml
site:
  photos:
    - {path: assets/photos/dining-room.jpg, alt: A candlelit table set for dinner., credit: 'Name, Unsplash'}
seed_artifacts:
  - {path: assets/photos/dining-room.jpg, encoding: base64, content: ...}
#+end_src

The plan step reads each photo's pixel size from its PNG, JPEG or WebP header and passes the list to the model as =supplied_photos=; a photo whose seed is missing or unreadable stops the step before any call. The builder then writes the list into the plan as =photos= (the model cannot change it), so any image slot may use a photo path as well as a planned art path, and pages render it at its real size. The prompts ask the plan to feature the photos where they fit and to draw art only for marks, motifs and diagrams. Photos never grow taller than the screen: a tall one crops to cover its box. Credits are kept in the plan for the operator; licensed stock such as Unsplash and Pexels needs no on-page credit, and the model may still show one in a caption.

* What the builder produces

From the plan, one specification per route and the artwork, =ls_components_compose()= renders:

- every planned page from the shared layout: skip link, header, visible primary navigation with =aria-current=, one =h1= (the first section's heading), footer, title, meta description, Open Graph tags and, when a site address is known, a canonical URL;
- the built-in =404.html=, =privacy.html= and =terms.html=, marked =noindex=, with honest draft wording;
- =styles.css=: tokens as custom properties, the base stylesheet, only the components that pages use, then the plan's signature CSS;
- =site.js=: the navigation enhancement plus the scripts of components that pages use;
- =robots.txt=, and =sitemap.xml= with the site address.

The site address comes from =options.base_url= on the pages step, else an =https://= =site.contact.url=. Without one there are no canonicals and no sitemap.

Navigation is visible without JavaScript at every width; =site.js= only adds a menu button on narrow screens after it initializes. A page never ships a folded-away desktop menu.

* The component library

Files live in =data/components/= and are embedded by =data/resources.xml=:

| File | Role |
|------+------|
| =catalog.yaml= | Components, variants and typed slots; the source of the model-facing reference |
| =NAME.html= | Section template in the Mustache subset below |
| =NAME.css=, =NAME.js= | Optional styles and behavior, included only when a page uses the component |
| =layout.html=, =section.html= | Page shell and section wrapper |
| =base.css=, =nav.js= | Shared styles and the navigation enhancement |
| =plan.schema.json= | Response schema for a plan |
| =pages/*.json= | Built-in utility page specifications |

Components (60, with 177 variants):

- Openings: =hero= (home only; statement, split, banner, centered, overlap, minimal), =cover= (home only; full-bleed, framed or split artwork), =poster= (home only; the title as the image: type, stamped, backdrop), =manifesto= (short stacked lines) and =page-header= (plain, split, band, rule, centered, minimal, giant; breadcrumb, key-fact strip, actions).
- Reading: =lead= (with optional drop cap), =text=, =article= (parts with inline figures, numbered notes), =figure=, =callout=, =quote=, =statement=, =table=, =glossary=, =columns=, =details= (collapsible panels) and =tabs=.
- Showcases: =showcase= (large panels, alternating, overlapping or full-bleed), =story= (steps scrolling beside a pinned artwork), =big-list= (an oversized typographic index of links), =profile= (one supplied person) and =badges= (supplied credentials only).
- Offers: =offer= (one highlighted package or ticket with its supplied price).
- Lists and navigation: =cards= (now also overlap, polaroid and minimal), =bento= (tiles of four sizes), =strip= (horizontally scrolling cards), =entries=, =filter=, =directory= (entries grouped by initial letter with a jump list), =links=, =pager=.
- Sequences: =features=, =split= (two panels), =steps=, =timeline=, =schedule=.
- Business facts: =facts=, =numbers=, =specs= (grouped specification sheets), =hours=, =location= (with a drawn map, never an embedded map service), =locations=, =areas= (places served), =contact-card=, =notice=, =menu= (sections, dotted leaders, supplied prices, tags; =all_label= adds a filter button per section, reusing the =filter= script and styles, and every dish stays visible without JavaScript), =services=, =pricing=, =checklist= (included and not included), =team= (supplied people only), =voices= and =partners= (supplied quotes and names only).
- Media and actions: =media=, =gallery=, =compare= (two artworks side by side), =marquee= (a scrolling band that stops for reduced motion and wraps instead), =cta=, =faq=, =form= and the =custom= escape hatch. =libresite --preview pages -r RECIPE= prints the full reference each writer receives.

Scripted components work without JavaScript: =tabs= shows every panel under its own heading until =site.js= turns them into an arrow-key tab list, and =filter= and =form= keep their fallbacks. =/components/every-variant= renders every component in every variant and requires styles for each non-default variant.

** Slot types

| Type | Value | Rendering |
|------+-------+-----------|
| text | string | HTML-escaped |
| rich | string in the rich-text subset | paragraphs, lists, strong, emphasis, code and checked links |
| link | ={href, label}= | =href= must be a planned route, =#id= on the page, =mailto:=, =tel:= or =https://= |
| links | list of link objects | the first is the primary action |
| image | ={src, alt}= | =src= must be planned art; width and height come from its ratio |
| items | list of objects with declared fields | converted recursively |
| fields | form fields | labeled controls with hints, errors and =aria-describedby= |
| choice, flag | listed value, boolean | as given |
| html | well-formed XHTML fragment (=custom= only) | sanitized: no scripts, forms, =h1=, style attributes, handlers or remote URLs |

Model text is data: plain slots are always escaped and rich text cannot emit raw HTML.

** Adding a component

Add an entry to =catalog.yaml=, write =NAME.html= and optional =NAME.css= and =NAME.js=, and list the files in =data/resources.xml=. No C changes are needed. Rules that span slots (for example "split heroes need art") belong in =check_component_rules()= in =src/core/ls-components.c=. Run =make tests=: the catalog is validated at load, and =/components/catalog= checks that the reference names every component.

Within an item, every declared field the model left out is set explicitly empty, so a template can never pick up an outer value of the same name (for example a menu-wide note inside a section). Templates receive, besides the converted slots: =component=, =variant=, =v_VARIANT= (true), =id=, =htag= (=h1= for the first section, else =h2=), =subtag=, =has_SLOT= for list slots, =has_text=, the interface strings (for example =required_label=), and per-component helpers: =n= and =n2= on items, =part_id= on article parts, =key= and =category_key= in =filter=, =section_id= and =section_key= on menu sections with =filtered= when =all_label= is set, =groups= (=letter=, =group_id=, =entries=) in =directory=, and the form view (=form_id=, =local=, =mailto=, =endpoint=, and per field =fid=, =describedby=, =is_input= and friends). Headings use =id="{{id}}-h"= so the section wrapper can label itself.

** Template subset

=ls_template_render()= supports ={{name}}= (escaped), ={{{name}}}= and ={{&name}}= (verbatim), ={{#name}}= sections over lists, objects and truthy values, ={{^name}}= inverted sections, ={{! comments }}=, ={{.}}= and dotted names resolved outward through the context stack. Malformed templates fail as =LS_ERROR_INVALID= and never produce partial output. There are no partials, lambdas or delimiter changes.

* Plan contract

Required: =name=, =tokens=, =nav=, =pages=, =art= (may be empty). The schema also requires =character= (see [[*Identities][identities]]). Optional: =tagline=, =lang=, =fonts=, =brand=, =action=, =footer=, =voice=, =css= and =ui= (interface strings for a non-English site).

- Tokens: seven =#rrggbb= colors with WCAG AA text pairs (ink and muted on paper and surface, accent_ink on accent, all 4.5:1), three font stacks of installed or generic families, and numeric scale, spacing, border, radius and heading settings within documented ranges.
- Fonts: up to three open-source families served by Bunny Fonts; the builder writes the stylesheet URL. Omit them when a brief forbids remote fonts.
- Routes are flat lowercase =.html= names including =index.html=; utility routes are built in and cannot be planned. Every =.html= path named by a =validate= step must be planned.
- Art is =assets/NAME.svg= with a ratio and a brief. Artwork must be a standalone SVG with a =viewBox= and the SVG namespace, under 256 KiB, with no scripts, foreign content, handlers, embedded images, stylesheets or external references.
- Plan and page CSS may not use =@import=, =</=, script URLs or =url()= outside =assets/= and =#ids=; braces must balance.

** Plan repair

=ls_components_repair_plan()= fixes mechanical misses before the plan is checked, so they never cost a model call: failing text colors move toward black or white only as far as 4.5:1 needs (a mid-tone accent is deepened when its text color cannot reach it), and numeric tokens clamp into range. The step reports repairs as progress. Everything else is the model's to fix.

* Parallel execution and threads

Worker threads only call =ls_provider_dispatch()=, which performs the transport call without emitting signals. The step thread pops each result, records usage with =ls_provider_record_usage()=, checks the answer and emits =progress=, so every pipeline, step and provider signal still runs on the calling thread. The first job to exhaust its retries cancels the rest, and the step returns only after every worker has finished. A cancelled run leaves the project untouched.

A provider used by a parallel =pages= step must support concurrent =generate= calls. The bundled =LsAiProvider= does: each call has its own client and ai-glib waits on a private main context. Set =parallel: 1= for a transport that cannot.

Usage for a pages step counts every call, so =attempts= is the number of calls and =retries= is =attempts - 1= by the usage record invariant, not the number of rejected answers. Elapsed time is the step's wall time.

* Checkpoints

A composed recipe's checkpoint fingerprint includes the component library digest, so changed templates or styles cannot resume against output rendered by an older library. Sealed packages do not yet archive the component library the way they archive scaffold bytes; a package whose recipe uses =pages= renders with the installed library.
