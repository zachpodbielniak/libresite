* Why it exists

Measured on the eight-page studio recipe, the file-bundle pipeline spent 28 to 37 minutes to ship 69 KB. Almost none of that was writing the site: it went to hidden thinking, resending rejected whole-site bundles, retyping pages in later passes, and eight model calls in a row. Only a quarter of what the model wrote was unique, visitor-facing work.

The component pipeline keeps the model on what is specific to a customer (the words and the facts) and lets the builder produce the rest deterministically. The same studio recipe now completes in about a minute of model time, with every page written at the same time. See [[*Measured runs][measured runs]] for current numbers.

* The pipeline

#+begin_src yaml
pipeline:
  steps:
    - {id: plan, type: plan, instructions: ...}
    - {id: pages, type: pages, options: {parallel: 12}, instructions: ...}
    - id: acceptance
      type: validate
      options: {required: [...], checks: [...]}
    - {id: build-notes, type: prune, options: {prefixes: [site/], archive: true}}
#+end_src

1. =plan= makes one model call and stores =site/plan.json=: design tokens, optional web fonts, brand, navigation, footer, voice, the brand mark and every route with a title, meta description and a short brief. Mechanical token misses are repaired natively (see [[*Plan repair][plan repair]]); anything else is rejected with every problem listed, and retried.
2. =pages= reads the plan and writes one page specification per route and the brand mark's SVG, all at once on worker threads, up to =options.parallel= (1 to 16, default 6) in flight. Each answer is checked on the step thread; a rejected answer is retried alone with its exact rejection. When every job is accepted the builder composes the whole site, runs the immediately following =validate= steps on the candidate, and sends a failure back to the one page that caused it. Nothing reaches the project until the composed site passes.
3. =validate= checks the composed files as with any recipe.
4. =prune= with =prefixes: [site/]= and =archive: true= takes the plan and page specifications out of the published site and keeps them in the run record (=.libresite/run.json=, member =archive=). They are the site's source: editing and theme switching work on them, and the pages are drawn from them.

=pages= with =options.mode: review= is an optional second pass: each writer receives its current specification and returns an improved one. The mark is kept.

Both steps are AI steps. They use the recipe's =ai= settings and a per-step =ai= override, like generation steps. They need a catalog with =spec_system= and the =plan=, =page=, =art= and =page-review= stages; replacement catalogs without them fail preflight. They generate new sites only; revise an existing project with generation steps.

* Page kinds

Every planned page has a =kind=, defined in =catalog.yaml=. A kind fixes which components may open the page and whether wide screens get an in-page contents column. Only =home= may open with a =hero= or =cover=; a =hero= or =cover= is rejected anywhere else, so interior pages never open like a landing page.

| Kind | For | Opens with | Contents column |
|------+-----+------------+-----------------|
| home | the front door (always =index.html=) | hero, cover or custom | no |
| index | lists: work, articles, services, locations | page-header | no |
| detail | one project, service, dish or product | page-header | yes |
| article | essays, guides, case studies | page-header | yes |
| menu | menus and price lists | page-header | no |
| visit | hours, address, directions | page-header | no |
| about | story, people, milestones | page-header | no |
| form | a page built around one task | page-header | no |
| services | what the business offers | page-header | no |
| pricing | packages and tiers | page-header | no |
| contact | ways to get in touch | page-header | no |
| gallery | a portfolio or photo page | page-header | no |
| events | dated events, places and how to join | page-header | no |
| general | anything else | page-header | no |
| utility | built-in 404, privacy and terms (not plannable) | page-header | no |

=page-header= renders a breadcrumb back home on every interior page. Reading kinds show a sticky contents column built from the page's headed sections and article parts once there are at least two; a page may add an =aside= rich-text note under it. Plan repair sets a missing kind (=home= for =index.html=, else =general=) and moves a misplaced =home= to =general=. The reference each writer receives lists every kind with its openings and suited components.

* Look

The =look= picks one value for each axis in =catalog.yaml= (=looks=), and the builder puts one class per axis on every page's =body=, for example =look-header-stacked=. =look.css= reshapes every component through those classes. The first value of each axis is its default. An unthemed site wears every axis at its default (see [[*The default design][the default design]]); a theme wears its own values. The other values stay in the library for themes and explicit options.

- header: bar, centered, stacked, inverted, floating, glass (sticky frosted bar)
- nav: underline, pill, caps, slashes
- heads: plain, rule, bar, split, giant (section heads are never numbered)
- buttons: square, pill, underline, offset, glass, hud (cut-corner monospace), chrome (Y2K metallic)
- panels (cards, tiles, boxed items across components): flat, outlined, raised, rules, inverted, glass (frosted translucent, solid without backdrop-filter or with reduced transparency), hud (cut corners, accent brackets, inner glow), deco (double-rule frames with stepped corners)
- rhythm: even, bands, divided, tight
- align: left, center
- images: plain, rounded, framed, print, shadow, taped (collage)
- footer: simple, big, inverted, sitemap (every planned page in columns)
- texture: none, grain, grid, dots, lines, aurora (fixed color fields for glass), scanlines, stars
- motion: none, rise (scroll-linked), reveal (the opening fades up on load), lift (cards and images lift under the pointer); all off for reduced motion. Pages also cross-fade between each other where browsers support view transitions, except for reduced motion.
- emphasis (words marked =*like this*= in section headings): accent, italic, highlight, underline, outline, block
- ornament between sections: none, wave, zigzag, dots, star, rule

On an unthemed site the stock flourishes (ornament, emphasis, kicker, backdrop, edges, texture and link style) are at their plain defaults, and the site's signature layer draws those details instead; see [[*Signature layer][the signature layer]].
- kicker labels: mono, pill, line, accent, number
- backdrop behind the opening section: none, glow, mesh, stripes, halftone, block, aurora, horizon (glowing perspective grid)
- art: open, line, flat, cutpaper, woodcut, blueprint, neon. The artist drawing the brand mark receives the value's description as TASK style.
- photos (supplied photographs): natural, duotone (ink and accent), mono, grain, print (a turned, white-bordered print), soft (an organic rounded mask)
- edges between sections with their own background: straight, wave, slant, torn, steps
- lettering: plain, dropcap, smallcaps, gradient (headline fades into the accent), outline
- links in running text: underline, thick, highlight, wavy, dotted
- frame (builder-owned): top, rail (a fixed navigation column), split (a sticky panel with the wordmark, tagline and navigation beside the content), center (a narrow journal column), wide (no column cap), offset (content right of an empty margin, headings hanging into it), masthead (a newspaper nameplate between rules). Rail, split and offset take effect from 64rem; below that every frame is a top bar.
- headpos (builder-owned): top, side (headings in a sticky column beside the content), center, hang (headings in the left margin)
- scheme: fixed, auto. Auto writes a second set of working colors for the visitor's other device scheme: a light site gains a dark version and a dark site a light one, derived from the tokens and repaired to the same AA pairs.

Section headings may mark one or two words as =*emphasis*=. The builder renders them as =<em class="em">= inside the heading only; contents entries, breadcrumbs, labels and anchors get the plain text, and unpaired or empty markers stay literal.

Plan repair fills a missing axis with its default, and resets a value the catalog no longer lists (such as the numbered section heads an existing site may still wear) to the default. Inverted areas swap the working color tokens locally, so every component inside them keeps its contrast pairs.

** Overrides

Every component can be overridden. =styles.css= declares =@layer ls-base, ls-modules, ls-components, ls-look, ls-signature=; the base stylesheet, each component's styles, the look and the site's signature layer sit in those layers, and everything else a site writes is unlayered after them:

1. =restyle=, a plan map from component name to CSS, is emitted after the look and only for components the site uses. Target =.NAME=, =.NAME--VARIANT= and =.NAME__PART=.
2. The plan's =css= follows, for site-wide signature rules.
3. Page =css= is inlined per page, and every section has an =id=.

Unlayered rules beat layered ones regardless of specificity, so an override never needs =!important= or longer selectors. The reduced-motion rules are layered =!important= declarations and still win. Restyle entries are checked like plan CSS (8 KB each, 24 KB in total).

The model-facing reference lists the axes and the override rules (LOOK and OVERRIDES). =/components/every-look= requires styles for each non-default look value, and checks that the plan schema lists exactly the catalog's axes and values; the schema's kind and look enums are generated from the catalog at load.

* The default design

The builder, not the model, decides the design. Until the hand-made templates exist, every unthemed site wears one calm design. It is the catalog's =default= block at the end of =catalog.yaml=:

#+begin_src yaml
default:
  opening: hero/centered
  photo_opening: hero/split
  scene: split
  palette: harbor
  typeface: geometric
  home: services-first
#+end_src

After the plan call, =ls_components_apply_default()= does the following:

- It sets =structure= to the home opening: =photo_opening= when the order supplies photos, else =opening=. The pages step rewrites the writer's first home section to that opening in the writer's own words (=ls_components_apply_opening()=). When the writer's words cannot fit it, or it needs a picture the site does not have, the default =opening= is used.
- It keeps only the brand mark in the plan's =art=. The art stage draws nothing else.
- Without a theme, it sets every look axis to its default, the colour tokens to the default palette, and the font tokens and web fonts to the default pairing (a plan without web fonts keeps its own installed stacks), and a visual sequence's layout to the default =scene=. The taste block's colour limit then applies.
- With a theme, the theme's look, colours and type stay; builder axes the theme leaves open take their defaults.

The same order always gets the same design, and two different businesses get the same look. Nothing is dealt from the recipe name or brief. The writer still chooses its sections, variants and words, in the order of the default home sequence.

The catalog checks the block at load: the openings are calm home openings, the scene is a scene variant, and the palette, typeface and home exist in =identities.yaml=. =tests/test-default.c= covers the look, the identity, themes, the openings, the mark, the retired structure, the retired look values and the demo flag.

* Structure

The plan's builder-owned =structure= object holds one member: =opening=, the home opening as component/variant, set by =ls_components_apply_default()=. The builder no longer deals page structure. Plans of existing sites may still carry the members an older builder dealt (=width=, =gutter=, =pace=, =pad=, =grid=, =scale=, =narrow=, =bleed=, =band=, =offset=, =loose=, =tight=, =variants=, =composition=, =kit=, =direction=, =forms=, =extras=, =angle= and =subject=). The plan check accepts them, so those sites can still be edited, and the renderer ignores them. Any other member is refused.

* Layout robustness

Themes and explicit looks put a component in many layouts: seven frames and four heading positions. The library therefore follows rules that hold in any column:

- Every grid track has a zero floor (=minmax(0, ...)=), and component lists, grids, rows, boxes and anything placed directly in a column may shrink below their longest word. A long word or wide picture can no longer widen a track and push items over their neighbours or off the page.
- Label-and-value rows (service, special and spec lines, opening hours, menu dishes and prices) wrap instead of forcing one line; nothing in a component forbids wrapping except the jump bar and the scrolling band, which scroll by design.
- Fluid type uses container units: =main= and the footer are inline-size containers, so display sizes follow the content column beside a side menu instead of the screen. Full-bleed pieces break out to that column and skip the offset margin and hanging-heading indent.
- Headings never hyphenate automatically. =site.js= shrinks any large text (22 px and up) whose longest word overflows its box, or whose box has been pushed past the right edge of a container, down to 30 percent of its size; without scripts such a word wraps at its last point. Headings hanging into the left margin are not treated as overflow.
- Side panels (rail and split frames) own their header: header looks built for a top bar are reset inside them, and the panel never wraps into a second column. No frame borders or insets the whole page: every site fills the screen.
- Split section titles and introductions share a row only when each can keep an 18rem reading column; otherwise they stack. Side-positioned section headings reserve at least 18rem rather than splitting a narrow column again. Phone layouts below the existing breakpoint are unchanged.
- Accent-painted variants and panels (=cta/band=, =statement/band=, =marquee/accent=, the offer stub, the accent notice box and the contrast split panel) take a local token swap, even against a plan restyle that colours their text with =var(--accent)=; so labels, rules, emphasis and buttons inside them stay visible. In the reading column, which has no page gutter, painted sections carry their own inset and a smaller heading.
- =--accent-text= is the accent only when it reads at 4.5:1 on both the paper and the surface tint; otherwise the builder deepens it toward the ink in the smallest step that does.
- The alternating =rhythm/bands= tint skips sections that paint their own colours (accent or surface variants), so their text keeps its contrast.
- A glass header pins only as a one-row bar (top, wide, offset frames) and reserves room at the top of the viewport, so jump-link targets and focused controls are not scrolled under it; in the centred and masthead frames, where brand, tagline and menu stack, it stays in place instead of covering a quarter of the screen. Its fill is 80 percent paper, so it reads even where a browser draws little blur.
- Sections with no padding of their own (a full cover, the jump bar) leave room above the next section; aside figures float only beside running text; a full cover grows to fit its text rather than letting it rise over the header, its picture fills the whole cell, and its text sits on a readable panel in the lower corner instead of a fade that washes out the photograph.
- Every component's layout breakpoints are container queries on the page column, not the screen. Side-by-side media and split covers follow the page column, so beside a side menu they stack before their text column gets narrow. Giant section headings step down beside a picture or a form.
- The offset frame adds its empty margin beside the column rather than taking it out, and its headings hang left even under centred alignment.
- A picture gets one frame: framed images skip the edge-to-edge cover and the framed media mount. Turned pictures (taped, print) are clipped at the page column so they never widen the page.
- Long email and web addresses in running text and in label-and-value fields (contact cards, spec sheets) get soft break points after =@= and =/= and before dots, so a narrow box breaks them at a seam rather than mid-word; link targets and short values are untouched.
- Galleries and photo strips give mixed portrait and landscape photographs one shape so rows stay even (masonry keeps each shape). The pinned story spaces its steps by a few lines, not by screens.

=/components/layout-lint= fails on a grid track without a zero floor, automatic hyphenation, a viewport unit inside a component, unwrappable text outside the two scrolling components, or a frame that borders the whole page.

=/components/section-layout-matrix= composes rail and top frames with side and top headings and three feature layouts, and checks that =styles.css= keeps the 18rem split track and the 18rem side column. Set =SECTION_LAYOUT_OUTPUT= and run the browser script to measure title and introduction widths and line counts at 390 and 1440. The regression was a seven-line heading in a 113px column; the rail example is two lines in about 342px. The changed rules sit inside the existing wide breakpoints, so the phone layout stays as it was. This uses saved synthetic content and the real composer, not a live generation or model evaluation.

#+begin_src sh
SECTION_LAYOUT_OUTPUT="$PWD/build/section-layout" build/release/test-section-layout
bash tests/section-layout.sh "$WEBDRIVER_URL" build/section-layout
#+end_src

A browser audit backs this up outside the test suite. A generated site places all 70 components in every variant (176 sections over 14 pages) with deliberately long words, is composed under each frame, and every page is checked at 1440, 1024, 768 and 390 px wide for pages that cannot scroll or scroll sideways, words wider than their box, text at the screen edge or jammed against a painted box, overlapping or clipped text, text shrunk below 11.5 px, and sections with no space between them. Findings fell from about 2,300 to under 90 during this pass; the remainder are sample prices and figures of fifteen-letter words in fixed-width stubs, which real content does not produce.

* Signature layer

Stock flourishes become fingerprints: once a visitor has seen the same double rule or highlighter stroke on two sites, every site that has it looks templated, however many other combinations exist. So the library owns structure (layout, spacing, phones, accessibility) and each unthemed site gets its own signature layer for the details people notice first.

- The pages step adds one more job beside the pages and the mark: the =signature= prompt stage sees the plan's name, character, voice, tokens, fonts and look, plus seven numbers dealt from the site (curve, rhythm, weight, angle, density, scale, roundness). It chooses one motif of the real business and returns ={"css": ...}= styling a fixed set of hooks: the divider between sections (=main > .block + .block::before=), marked words (=.em=), labels (=.kicker=), section headings, the page opening, header, footer, links and selection.
- =ls_components_check_signature()= accepts only CSS of at most 8000 bytes whose colours are the site's custom properties (no literals, =rgb()=, =hsl()= or =color-mix()=), whose =url()= values are percent-encoded SVG data images without scripts or links, and which never uses =display: none=, =visibility: hidden=, =position: fixed=, =!important=, imports or markup. A rejected layer goes back once with the reason; a layer that never passes is left out and the site builds plainly. It never falls back to a stock flourish.
- The accepted layer is kept as =site/signature.css= beside the page specifications, so rebuilds and reviews reuse it, and joins the plan as its builder-owned =signature= member when the site is composed.
- In =styles.css= it sits in the last cascade layer, =@layer ls-base, ls-modules, ls-components, ls-look, ls-signature=: it leads over every library rule, the site's own plan CSS and restyles still lead over it, and a few library guards declared =!important= in an earlier layer (focus rings, the page-header index label) hold against it.
- Themed sites and page reviews write no new signature; a replacement prompt catalog without the =signature= stage simply goes without one.

Live runs of the bookshop and the dog farm each wrote their layer in about 21 seconds, beside the pages and inside the usual build time, first try: drawer-pull dividers, shelf-bay lines behind the opening and a brass rule for the bookshop; fence-rail dividers with posts, a post line along the header and footer and a lattice edge for the dog farm.

* Clone check

The customer sees one site, so the builder no longer measures how alike sites are. One check stays: a site may not copy an earlier site's signature layer.

- The pages step writes =site/fingerprint.json= beside the plan, from =ls_components_fingerprint()=: every look axis except the stock flourishes, the paper, ink and accent colours, the display and body families, the home page's opening (component and variant) and its section sequence, and up to 300 hashed shape-carrying declarations of the signature layer. It holds no copy, facts or photographs. The prune step archives it with the plan, so it never ships.
- An embedder keeps the fingerprints of delivered sites and passes the ones that matter (the same trade, the same area) back as =site.avoid= on the next order, up to 500 of them. The builder keeps =site.avoid= out of every prompt.
- A signature layer whose hashed declarations overlap an avoided site's by =LS_COMPONENTS_SIGNATURE_TOO_CLOSE= (half) or more is sent back with the reason (=ls_components_signature_overlap()=); like any failing layer, one that never clears is left out.

=/pages/clone-check= builds one order, then the same order with the first site as =site.avoid=, and checks that the repeated signature layer is refused.

* Missing facts

A thin order makes a thin site, and a site should not guess an address or an event date. So the plan names what is missing: =plan.missing= holds up to 12 short questions (at most 200 characters each) about facts a visitor to this kind of business would expect that the order did not supply, such as opening hours, prices or a date. The pages write around those gaps rather than filling them. The plan step reports them as one progress line, =facts to ask the owner: ...=, and the plan keeps them in the run record, so whoever gathers the order can ask the owner and build again.

Those questions are for the owner, never for visitors. Any text a visitor can read (page slots, the footer note, titles and descriptions) that talks about inputs nobody supplied is refused and sent back with the reason: phrases such as "have not been supplied", "not supplied", "were not provided", "to be confirmed", "to be announced", "details to come", "will be posted", "not published yet" and the words TBD, TBC and TBA, matched as whole words in any case. A missing item is left out silently.

* Footer credit

A caller, such as a hosting service, may pass one credit line for the footer as =site.credit: {text, url}=: =text= one line of 1 to 80 characters and =url= an https:// address with a host, at most 300 bytes, without spaces, quotes or angle brackets (=ls_credit_valid()=). The plan step copies it into the plan as =credit=, and every page, the built-in 404, privacy and terms pages included, ends its footer with it:

#+begin_src html
<p class="wrap site-footer__credit"><a href="https://example.com/" rel="noopener">Built with Example</a></p>
#+end_src

It is small and unobtrusive in the site's own style: the muted text colour (checked at 4.5:1 on the footer surface) at the smallest step, under everything else in the footer. The text is escaped and shown exactly as supplied. No model is shown it, so no page repeats it, and an edit cannot change it; edits keep it. Without =site.credit= nothing is drawn.

* Language and spelling

Copy follows the business's locale: =languages.default= (such as =en-GB= or =en-AU=) or a place the brief names. When none is given the writers use US English spelling and usage (color, neighborhood, center). This is a prompt instruction; offline tests check that it is in the prompt, not the spelling of live output.

* Themes

A theme is a complete design applied to the whole site: every token, the web fonts, one value for every look axis and signature CSS. =data/components/themes.yaml= bundles twenty-four: swiss (white, black and red, ruled section heads, a sitemap footer), magazine (Didone headlines, drop caps, split headings), terminal (phosphor monospace, scanlines), collage (taped images, turned prints, torn edges), deco (green and gold, stepped double frames), chrome (Y2K chrome buttons over a color mesh), editorial, brutalist, midnight, soft, civic, atelier, workshop, neon, terracotta, nordic, retro, zine, botanical, noir, sunrise, liquid-glass (frosted glass over dawn color fields), orbital (sci-fi mission control: HUD panels, scanlines, a horizon grid) and hologram (glass panels glowing over a violet starfield). Every component draws only on tokens and look classes, so applying a theme changes every component on every page together, while content, routes, navigation, the mark and component choices stay as they are. Themes whose look used numbered section heads now use ruled heads.

Name one on the plan step:

#+begin_src yaml
- {id: plan, type: plan, options: {theme: midnight}}
#+end_src

The plan call then uses a schema without tokens, fonts, look, css and restyle, and TASK carries the theme's name and summary, so the model writes only content and structure and returns a shorter plan. The builder applies the theme to the answer before repairing and checking it. The plan options are =theme= and =sector= (see [[*Identities][identities]]; the sector no longer changes the design); an unknown theme or sector fails preflight with the list of choices.

=ls_components_apply_theme()= does the same to any plan: it replaces the design half and leaves the rest. Themes are checked like plans when the library loads (contrast, token ranges, fonts, CSS), so applying one can never produce a plan that fails its own checks, and the library's copy is never edited. To add a theme, add an entry with a summary, all tokens, fonts, every look axis and optional css or restyle; =/components/themes= composes the fixture site under every theme.

Recomposing an already delivered site needs its plan and page specifications. Composed recipes archive them in the run record (see [[*The pipeline][the pipeline]]); a command that recomposes a delivered site from them is not built yet.

* Identities

=data/components/identities.yaml= defines business sectors (trades, food, community, advisory, software, creative, retail and wellness), twenty-one palettes, fifteen type pairings and sixteen home-page section sequences, each listing the sectors it fits. =data/components/pairings.yaml= adds a curated library of more type pairings, joined to the typefaces at load. Each palette and pairing is checked like a plan when the library loads (contrast, fonts, token ranges), and none may be the house default.

The builder deals nothing from this library. The catalog's =default= block names one palette, one type pairing and one home sequence (see [[*The default design][the default design]]), and =ls_components_get_default_identity()= returns them. TASK carries them as =palette= (name, summary, the seven color tokens), =type= (name, summary, font tokens and Bunny Fonts families) and =home= (component names after the opening). The rest of the library stays as data for the templates to come.

The plan step still accepts =sector= and checks it against the list, so existing recipes keep working, but the sector no longer changes the design.

The plan starts with =character=: one or two sentences on what the business looks like in the real world. The writers draw on it for concrete words. =ls_components_check_identity()= rejects a plan that falls back on the house default, warm cream paper with a rust or orange accent or Fraunces over Source Sans, unless the identity itself is that warm. =character= is required by the plan schema and optional natively, up to 600 characters.

=/components/identities= checks the default identity and the house-default rejection; =/pages/plan-identity= checks the prompt and the stored plan.

* Photographs

A recipe can supply real photographs, such as the customer's own or licensed stock. Each is a binary seed artifact under =assets/= (=encoding: base64=) listed in =site.photos= with its alt text and an optional credit:

#+begin_src yaml
site:
  photos:
    - {path: assets/photos/dining-room.jpg, alt: A candlelit table set for dinner., credit: 'Name, Unsplash'}
seed_artifacts:
  - {path: assets/photos/dining-room.jpg, encoding: base64, content: ...}
#+end_src

The plan step reads each photo's pixel size from its PNG, JPEG or WebP header and passes the list to the model as =supplied_photos=; a photo whose seed is missing or unreadable stops the step before any call. The builder then writes the list into the plan as =photos= (the model cannot change it), so any image slot may use a photo path, and pages render it at its real size. The prompts ask the plan to feature the photos where they fit. The builder draws no pictures: picture slots take supplied photos, and the only artwork is the brand mark. Photos never grow taller than the screen: a tall one crops to cover its box, and a photo in the page's opening stays under 60 percent of the screen height so the headline is on the first screen. A photo may name a =focus=, one or two of =left=, =center=, =right=, =top=, =bottom=, or two percentages such as =70% 30%=; the builder writes it as the image's crop position so the subject stays in frame. Credits are kept in the plan for the operator; licensed stock such as Unsplash and Pexels needs no on-page credit, and the model may still show one in a caption.

The plan step also sizes every photo for phones: a capped largest size and smaller widths as WebP, stored in the plan as =variants= and shown with =srcset=, =sizes= and the capped dimensions, while an oversized original moves to the run record instead of the published site. Small photos are published as supplied. See [[file:images.org][photographs sized for phones]] for the caps, defaults and =options.images=.

* Social profiles and sharing

A recipe can list the business's own social profiles. Nothing is generated: the builder links only the addresses supplied, and a site without them has no social links.

#+begin_src yaml
site:
  social:
    - {url: 'https://www.instagram.com/bandlpawhaven'}
    - {url: 'https://www.facebook.com/bandlpawhaven'}
    - {url: 'https://harbor.example/journal', label: Our journal}
#+end_src

Each entry is an https:// address of up to 300 characters with no spaces or quotes, and an optional label of up to 60 characters; at most 12, each once. The plan step recognises the network of each address from =data/components/networks.yaml= (a listed host or one of its subdomains, or a federated =/@name= path for Mastodon; anything else is =web=), derives the handle visitors see, and writes the list into the plan as =social= after the model answers, replacing anything the model wrote. =ls_components_social()= exposes the same recognition.

With profiles, the builder adds:

- a row of network icons in every page footer, each link named for screen readers and marked =rel="me"=;
- Organization JSON-LD with =sameAs= links on the home page, with =url= when the site has an address;
- the =social= component (cards, row, list or band), which pages may use only when the plan lists profiles. Composition refuses a =social= section on a site without them.

The =share= component (row, stacked, quiet or pills) offers email, Facebook, X, LinkedIn, WhatsApp and Bluesky links, a copy-link button and the device share sheet. With a site address (=pages.options.base_url= or the recipe's deployment URL) the links are complete in the HTML; without one they stay hidden until =site.js= fills them from the visitor's own address. Copy and the share sheet appear only where the browser supports them. Nothing loads from any network until a visitor follows a link: there are no embedded widgets, trackers or third-party scripts.

With a site address, a page whose first picture is a supplied photograph (PNG, JPEG or WebP) gets =og:image= and a large preview card; drawings are not used as previews. A sized photo previews as its largest WebP variant.

* Supplied form

A site has one live form when the recipe names it in =site.form=: where it posts and exactly which fields it sends. The host behind the site, not libresite, receives and handles the submission.

#+begin_src yaml
site:
  form:
    action: /api/forms/contact
    honeypot: website
    fields:
      - {name: first-name, label: First name, required: true, autocomplete: given-name}
      - {name: last-name, label: Last name, required: true, autocomplete: family-name}
      - {name: email, label: Email, type: email, required: true, autocomplete: email}
      - {name: message, label: Message, type: textarea, required: true, maxlength: 4000}
#+end_src

=action= is a same-site path (one leading =/=, letters, digits, =/=, =_=, =.= and =-=, no =..=) or an https:// address, at most 300 characters, never with =?= or =#=. A same-site path keeps the page free of backend addresses and accounts: the host decides where a submission goes, so a site moves between hosts or backends without a rebuild. There are 1 to 12 fields, each once, named with lowercase letters, digits, =-= or =_=; =type= is =text= (the default), =email=, =tel=, =url=, =number=, =date= or =textarea=; =required= is a boolean; =autocomplete=, =maxlength= (1 to 20000) and =hint= are optional. =honeypot= optionally names a field, not among the others, that the page hides from people; a host can discard any submission that fills it.

The plan step writes the form into the plan as =form= after the model answers, replacing anything the model wrote, and a model edit cannot change it. A trusted caller replaces or removes that plan member with =ls_editor_replace_form()= (=ls_form_valid()=); see [[file:editing.org][editing]]. Every =form= section on the site then renders in endpoint mode with that action and those fields, whatever mode, target or fields the model wrote; the model writes only the heading, the words around the form and the button label. Without =site.form=, a form section keeps its own =local=, =mailto= or =endpoint= mode, and an endpoint target may be a supplied https:// address or same-site path.

An endpoint form is an ordinary =POST= of URL-encoded fields, so it works without scripts. With =site.js= it sends the same fields in the background, disables the button while pending, reports the =sending= interface string in a polite status region, asks for JSON, and after an answer that the message was received clears the form and shows a confirmation panel in its place; after a refusal or a failure it shows the =send_failed= string in an error banner, marks the field the host named and keeps every entry. Without scripts the host's own answer is what the visitor sees (see [[*Confirmation after sending][confirmation after sending]]). Offline tests check the rendered markup and script; they do not exercise a host or a browser submission.

* Podbay modules

A site can carry site features from podbay, the catalog of first-party modules, such as a booking or contact form. The platform that orders the site loads each module with podbay's library, draws its default snippet with =pb_module_render()= and its stylesheet with =pb_module_get_css()=, and passes both in =site.modules=; libresite does not link podbay and never receives submissions.

#+begin_src yaml
site:
  modules:
    - id: contact-form
      title: Contact us
      snippet: |
        <form class="podbay podbay-contact-form" hx-post="/forms/contact" hx-target="#contact-result" hx-swap="innerHTML">
        <div class="podbay-field"><label for="contact-email">Email</label><input id="contact-email" name="email" type="email" maxlength="254" required></div>
        <button type="submit">Send message</button>
        <div id="contact-result" class="podbay-outcome" data-podbay-outcome="thank-you" aria-live="polite"></div>
        </form>
      css: |
        .podbay-contact-form { display: grid; gap: var(--podbay-gap, 1rem); }
#+end_src

There are 1 to 8 modules with unique ids (podbay's grammar: lowercase words joined by single hyphens, at most 64 characters) and an optional title of up to 80 characters. Both texts are checked before anything is generated (=ls_module_check_snippet()=, =ls_module_check_css()=), again when the plan is checked, and so again when an edit recomposes a site:

- The snippet must be exactly one =form= of podbay's restricted markup, at most 64 KiB: class =podbay podbay-ID=; =hx-post= a same-site path or https:// address under the same rules as =site.form= actions; =hx-target= =#= and the id of an element in the snippet; =hx-swap= one of podbay's eight modes; optional =hx-encoding= =multipart/form-data=. Inside it only =div=, =label=, =input= (text, email, tel, url, number, checkbox, date, time or file), =textarea=, =select=, =option= and submit =button= elements, each with attributes from a fixed list, double-quoted values, unique ids, at least one button, and text and values that use only =&amp;=, =&lt;=, =&gt;=, =&quot;= and numeric references. Scripts, styles, event handlers, links, images, comments and anything else are refused with the reason.
- The stylesheet follows podbay's rules: at least one rule, only flat rules, every selector starting with =.podbay-ID= and not extending that class name, none of =@ \ < " ' ! &= (so no at-rules, imports, escapes, strings or =!important=) and only the functions =var=, =calc=, =min=, =max=, =clamp=, =rgb=, =rgba=, =hsl=, =hsla=, =not=, =is=, =where=, =nth-child= and =nth-of-type=, so it fetches nothing.

The plan step writes the modules into the plan as =modules=, replacing anything the model wrote, and an edit cannot change them. The planner, page writers and the editor see only each module's id and title. A page places a module with a =module= section: =module= is the id, and the model writes only an optional heading and body; a section naming a module the plan does not list is refused, and each module appears at most once on a page so its element ids stay unique.

The page carries the snippet as it was supplied, with one change: the =form= also gets =action= and =method="post"= from its =hx-post=, so it posts as an ordinary form without scripts, plus =data-podbay-form= and =data-failed= (the site's =send_failed= words). Only a site whose pages place a module ships any of this:

- =styles.css= puts each placed module's stylesheet in its own cascade layer, =ls-modules=, before =ls-components=. The =module= component's styles in the later layer set podbay's =--podbay-*= custom properties from the site's tokens (spacing, lines, radius) and give labels, fields and the submit button the site's type and button look, so the module matches the site without editing its file. A plan =restyle= for =module= or the site's own CSS still leads over both.
- =site.js= gains =module.js=: with scripts, a module form sends its fields in the background as htmx would, with =HX-Request: true=, and places the host's answer into its =hx-target= with its =hx-swap=; elements of the answer marked =hx-swap-oob= replace the page element with the same id. The answer is parsed with =DOMParser=. Before it is placed, the script drops scripts, embedded documents (=iframe=, =object=, =embed=), =base=, =meta=, =link= and =template= elements, =svg= and =math= (an =animate= or =set= can write a handler onto a live node after the walk), event handler attributes, and =javascript:=, =vbscript:= and =data:= addresses on =href=, =src=, =action=, =formaction=, =xlink:href=, =srcset= and =poster=. Nothing in the answer runs. A 2xx answer clears the form. When nothing comes back, or the network fails, the target shows the =send_failed= words and every entry is kept. A page that loads htmx itself is left to htmx.

podbay's specification also lets the builder draw its own markup from a module's data definition instead of the default snippet; libresite currently draws the supplied snippet. Offline tests check the checks, the composed markup and styles, and the script's text; they do not run a host, htmx or a browser submission.

* Call and quote actions

A business site should turn a visitor into a call or a quote request in one tap. The order supplies the facts; the builder draws the actions and never invents them.

#+begin_src yaml
site:
  contact:
    phone: '+1 (555) 014-2270'
    email: hello@harbor.example
  form: {action: /api/forms/contact, fields: [...]}
#+end_src

=site.contact.phone= is a phone number as a person writes it: digits, spaces, =+=, =.=, =-=, =(= and =)= only, at most 40 characters, 3 to 15 digits, and a =+= only before the first digit. =site.contact.email= is one plain address (one =@=, a dotted domain of letters, digits, =.= and =-=, no spaces, quotes, brackets or =?=, =#= and =%=, at most 254 characters). Both are optional; recipes and forms with anything else are refused with the rule. =ls_phone_tel()= builds the =tel:= address from the =+= and the digits only, so =+1 (555) 014-2270= links to =tel:+15550142270= and is shown as written.

The plan step writes the supplied phone and email into the plan as =contact= after the model answers, replacing anything the model wrote; other contact facts (address, url) are not copied. An edit cannot change it. With them the builder adds:

- an action bar on every page: a =nav= landmark named by the =quick_actions= interface string (default "Get in touch") at the end of =main=, kept at the bottom of the screen with =position: sticky= while the page scrolls and settling above the footer at its end, so it is on the first phone screen and in reach on every screen after. It holds exactly one primary action, never three of equal weight: the "Book online" button when the order supplies a booking page (see below), else a call button (the =call= string and the number as supplied) when there is a phone, else a request-a-quote link (the =quote= string, default "Request a quote") when the site has a supplied form, leading to the first planned page that shows a =form= section, at that section (for example =contact.html#quote=). The bar's button is at least 44 px tall, use the site's checked button colours, keep the global focus ring, add no motion, are hidden in print, and reserve =scroll-padding-bottom= so a focused control is never left under the bar. Without a phone and without a supplied form there is no bar;
- the =call= component (panel, band, inline), which pages may use where a visit invites a call, usually the contact or visit page. The model writes only an optional heading and body; the builder draws the number, the =tel:= link and a =mailto:= link when an email was supplied. Composition refuses a =call= section on a planned page of a site without a phone;
- the supplied phone repeated as a call link in the confirmation panel that replaces a live form after sending (see [[*Confirmation after sending][confirmation after sending]]).

Without a phone the site has no =tel:= link from the builder, no call button and no call section, and nothing is put in their place.

** Book online

A host that takes bookings for the business passes where they happen as =site.booking: {href}=: a same-site path such as =/book=, or an https:// address, under the same rules as a supplied form's =action= (=ls_booking_valid()=). The plan step copies it into the plan as =booking=, replacing anything the model wrote, and every page's action bar then holds a "Book online" button (the =book= interface string) as its one primary action, in place of the call and quote actions. The phone stays on the page in call sections and the contact card. No model is shown the address, and an edit cannot change it. Without =site.booking= nothing is drawn.

The =booking-calendar= component puts the host's open times on a page. For a bookable site, composition places one on the booking page (=book.html=, =booking.html= or a =reserv*= route), or on the contact page, or on the visit page, whichever of those exists and still has room for a section. A page is not chosen because its name contains those letters (=facebook.html= stays a normal page). A recipe may place the component explicitly, and that explicit section is the only one. The builder supplies the address from =site.booking= and preserves the "Book online" action. The script requests =GET <href>?format=json=. Venture's public booking page returns a JSON array, not an envelope: =[{"start":"2026-10-27T14:00:00Z","end":"2026-10-27T14:30:00Z","label":"Tue 27 Oct 2026 10:00 UTC","day":"2026-10-27"}]=. =day= is the business-local date and =label= is the host's own local text; =start= is the UTC value to book. There is no =time_zone= field. An object whose =slots= member is that same array is accepted as well. A day with no slots is unavailable, and the month opens on the earliest open day. The visitor chooses a day and time, enters name, email and an optional note, and the script sends =POST <href>= with JSON =start=, =name=, =email= and =notes=. HTTP 201 confirms in place and hides the month; HTTP 409 drops that time and asks for another. Any other failure keeps the form and says the booking was not confirmed. The host owns conflict checks and notifications. If scripts or availability fail, the ordinary booking link remains. The form links =privacy.html= and =terms.html= before the name, email and note fields. Use a same-site =href= such as =/book= or =/book/<slug>= so the browser can read the JSON without cross-origin permissions. See [[file:../recipes/booking-calendar.yaml][the example recipe]] and the recorded phone pass [[file:media/booking-calendar-demo.mp4][booking-calendar-demo.mp4]].

Icons come from Simple Icons 16.33.0 (CC0 1.0). Brand marks remain their owners' trademarks and link only to the business's own profiles. LinkedIn has no Simple Icons mark, so it and unrecognised hosts use the builder's own link glyph. A library archived before =networks.yaml= existed still loads, with the link glyph for every profile.

* Confirmation after sending

A visitor who sends a live form stays on the page. There is no thank-you page: a confirmation panel takes the form's place, so the page they were reading, the call button and the navigation stay where they were.

Every endpoint form renders, just before the =form= element and inside a =form__body= wrapper, a hidden panel:

#+begin_src html
<div class="form__sent" role="status" aria-live="polite" tabindex="-1" data-form-sent hidden>
<p class="form__sent-message">Thank you. Your message was sent.</p>
<p class="form__sent-actions"><a class="button form__sent-call" href="tel:+15550142270">Call <span class="form__sent-number">+1 (555) 014-2270</span></a>
<a class="form__sent-again" href="#contact-form" data-form-again>Send another message</a></p>
</div>
#+end_src

The message is the =sent= interface string, the call link the supplied phone (left out when the site has none, so nothing is invented), and the last link the =send_another= string (default "Send another message"), which brings the form back. The panel is a polite status region, takes focus with a visible ring (=3px solid var(--focus)=) when it appears, uses ink on surface, a pair the builder checks for contrast, and has no animation.

The panel has no id and the builder reserves none: the script finds it as the panel just before its form, and moves focus to the element itself. Only the script shows it; the stylesheet never does, so without scripts it stays hidden.

The host decides nothing about display; the page does. Libresite's script follows the host's form answers described below; it never receives submissions itself.

*With scripts*, the form posts its fields in the background with =Accept: application/json=:

| Answer | What the page does |
|--------+--------------------|
| 2xx with JSON ={"status": "received", ...}= | clears and hides the form, shows the panel, moves focus to it and scrolls it into view |
| JSON ={"error": ..., "field": NAME, ...}= (422) | shows the =send_failed= string in the error banner (=role="alert"=), marks the form field named =NAME= with =aria-invalid= and the =error_invalid= string in its error slot, and moves focus to it |
| JSON error with =field: null= (400, 429, 503) | shows the error banner and scrolls it into view |
| anything else: a 2xx that is not ="received"=, an answer that is not JSON, or no answer at all | shows the error banner |

Every refusal keeps the form and every entry; the next send clears the marks first. The visible words are the site's own interface strings, in the site's language; the host's English =message= is not shown. Scrolling is instant when the visitor prefers reduced motion.

*Back from a send without scripts.* The host answers a plain =POST= with =303 See Other=: to the site's =thank_you= address when it sets one, otherwise back to the page the form was sent from with =?sent=1= or =?error=CODE= (=CODE= a field name, =invalid=, =rate-limited= or =unavailable=), and no fragment. When a page opens with =?sent=1=, the script shows the panel of the page's first live form as above; with =?error=CODE= it shows that form's error banner and marks the field =CODE= names, if the form has one. A visitor with no scripts at all sees the page again with the form, since nothing shows the panel without a script: a site that wants a confirmation for those visitors has the host redirect to a page of its own.

* What the builder produces

From the plan, one specification per route and the mark, =ls_components_compose()= renders:

- every planned page from the shared layout: skip link, header, visible primary navigation with =aria-current=, one =h1= (the first section's heading), footer, title, meta description, Open Graph tags and, when a site address is known, a canonical URL;
- the built-in =404.html=, =privacy.html= and =terms.html=, marked =noindex=, with honest draft wording;
- =styles.css=: tokens as custom properties, the base stylesheet, only the components that pages use, then the plan's signature CSS;
- =site.js=: the navigation enhancement plus the scripts of components that pages use;
- =robots.txt=, and =sitemap.xml= with the site address.

The site address comes from =options.base_url= on the pages step, else an =https://= =site.contact.url=. Without one there are no canonicals and no sitemap.

Navigation is visible without JavaScript at every width; =site.js= only adds a menu button on narrow screens after it initializes. A page never ships a folded-away desktop menu.

- Food and classes: =recipe= (facts, ingredients and numbered method), =specials= (a board or list of supplied dishes and prices), =timetable= (days of sessions).

A closing time earlier than the opening time runs past midnight. Without the script, or with an unknown zone, the badge stays hidden and the table still shows the hours. =areas= gains a =map= variant: the business at the center with the places in rings.
- Media and actions: =media=, =gallery= (every picture links to its file; =site.js= opens it in a dialog instead), =carousel= (a swipeable row with previous and next buttons), =compare= (two artworks side by side; the =slider= variant lays one over the other with a range control to wipe between them), =marquee= (a scrolling band that stops for reduced motion and wraps instead), =cta=, =faq=, =form= and the =custom= escape hatch. =libresite --preview pages -r RECIPE= prints the full reference each writer receives.

Scripted components work without JavaScript: =tabs= shows every panel under its own heading until =site.js= turns them into an arrow-key tab list, and =filter=, =form=, =carousel=, =gallery=, the =compare= slider and the open-now badge keep their fallbacks. With scripts, the enlarged-picture dialog is named after its picture, and the =compare= slider keeps its range control in its own row below both stacked pictures, with a thin line at the split. When only some =products= have pictures, the others get a quiet frame of the same shape so the grid stays even.

Artwork has no lettering: no words, initials, labels, codes or numbers. It is shown through =<img>=, where the site's web fonts never load, so SVG text renders in fallback glyphs. The artwork check rejects =<text>=, =<tspan>= and =<textPath>=, and that artwork is retried; words belong in the page. Edge looks (wave, torn, slant, steps) cut into the bottom of each section, so those sections get extra bottom padding equal to the cut and their content is never clipped.

The plan's =nav= links may carry =children= (up to 8 planned pages each). On wide screens they open as a drop-down on hover or keyboard focus; in the phone menu they sit indented under their parent, and the parent is marked while one of its pages is open. =/components/every-variant= renders every component in every variant and requires styles for each non-default variant.

** Slot types

| Type | Value | Rendering |
|------+-------+-----------|
| text | string | HTML-escaped |
| rich | string in the rich-text subset | paragraphs, lists, strong, emphasis, code and checked links |
| link | ={href, label}= | =href= must be a planned route, =#id= on the page, =mailto:=, =tel:= or =https://= |
| links | list of link objects | the first is the primary action |
| image | ={src, alt}= | =src= must be planned art; width and height come from its ratio |
| items | list of objects with declared fields | converted recursively |
| fields | form fields | labeled controls with hints, errors and =aria-describedby= |
| choice, flag | listed value, boolean | as given |
| html | well-formed XHTML fragment (=custom= only) | sanitized: no scripts, forms, =h1=, style attributes, handlers or remote URLs |

Model text is data: plain slots are always escaped and rich text cannot emit raw HTML.

** Adding a component

Add an entry to =catalog.yaml=, write =NAME.html= and optional =NAME.css= and =NAME.js=, and list the files in =data/resources.xml=. No C changes are needed. Rules that span slots (for example "split heroes need art") belong in =check_component_rules()= in =src/core/ls-components.c=. Run =make tests=: the catalog is validated at load, and =/components/catalog= checks that the reference names every component.

Within an item, every declared field the model left out is set explicitly empty, so a template can never pick up an outer value of the same name (for example a menu-wide note inside a section). Templates receive, besides the converted slots: =component=, =variant=, =v_VARIANT= (true), =id=, =htag= (=h1= for the first section, else =h2=), =subtag=, =has_SLOT= for list slots, =has_text=, the interface strings (for example =required_label=), and per-component helpers: =n= and =n2= on items, =part_id= on article parts, =key= and =category_key= in =filter=, =section_id= and =section_key= on menu sections with =filtered= when =all_label= is set, =groups= (=letter=, =group_id=, =entries=) in =directory=, and the form view (=form_id=, =local=, =mailto=, =endpoint=, and per field =fid=, =describedby=, =is_input= and friends). Headings use =id="{{id}}-h"= so the section wrapper can label itself.

** Template subset

=ls_template_render()= supports ={{name}}= (escaped), ={{{name}}}= and ={{&name}}= (verbatim), ={{#name}}= sections over lists, objects and truthy values, ={{^name}}= inverted sections, ={{! comments }}=, ={{.}}= and dotted names resolved outward through the context stack. Malformed templates fail as =LS_ERROR_INVALID= and never produce partial output. There are no partials, lambdas or delimiter changes.

* Plan contract

Required: =name=, =tokens=, =nav=, =pages=, =art= (may be empty; the builder keeps only the brand mark). The schema also requires =character= (see [[*Identities][identities]]). Optional: =tagline=, =lang=, =missing= (see [[*Missing facts][missing facts]]), =fonts=, =brand=, =action=, =footer=, =voice=, =css= and =ui= (interface strings for a non-English site). The builder writes =structure=, =photos=, =social=, =form=, =contact=, =modules=, =booking=, =credit= and =demo= from the order (see [[*Call and quote actions][call and quote actions]]); a model answer never sets them.

- Tokens: seven =#rrggbb= colors with WCAG AA text pairs (ink and muted on paper and surface, accent_ink on accent, all 4.5:1), three font stacks of installed or generic families, and numeric scale, spacing, border, radius and heading settings within documented ranges.
- Fonts: up to three open-source families served by Bunny Fonts; the builder writes the stylesheet URL. Omit them when a brief forbids remote fonts.
- Routes are flat lowercase =.html= names including =index.html=; utility routes are built in and cannot be planned. Every =.html= path named by a =validate= step must be planned.
- Art is the brand mark, =assets/NAME.svg= with a ratio and a brief; other planned artwork is dropped. Artwork must be a standalone SVG with a =viewBox= and the SVG namespace, under 256 KiB, with no scripts, foreign content, handlers, embedded images, stylesheets or external references.
- Plan and page CSS may not use =@import=, =</=, script URLs or =url()= outside =assets/= and =#ids=; braces must balance.

** Plan repair

=ls_components_repair_plan()= fixes mechanical misses before the plan is checked, so they never cost a model call: failing text colors move toward black or white only as far as 4.5:1 needs (a mid-tone accent is deepened when its text color cannot reach it), numeric tokens clamp into range, and look values the catalog no longer lists take their defaults. The step reports repairs as progress. Everything else is the model's to fix.

* Parallel execution and threads

Worker threads only call =ls_provider_dispatch()=, which performs the transport call without emitting signals. The step thread pops each result, records usage with =ls_provider_record_usage()=, checks the answer and emits =progress=, so every pipeline, step and provider signal still runs on the calling thread. The first job to exhaust its retries cancels the rest, and the step returns only after every worker has finished. A cancelled run leaves the project untouched.

A provider used by a parallel =pages= step must support concurrent =generate= calls. The bundled =LsAiProvider= does: each call has its own client and ai-glib waits on a private main context. Set =parallel: 1= for a transport that cannot.

Usage for a pages step counts every call, so =attempts= is the number of calls and =retries= is =attempts - 1= by the usage record invariant, not the number of rejected answers. Elapsed time is the step's wall time.

* Checkpoints

A composed recipe's checkpoint fingerprint includes the component library digest, so changed templates or styles cannot resume against output rendered by an older library. Sealed packages do not yet archive the component library the way they archive scaffold bytes; a package whose recipe uses =pages= renders with the installed library.

A read-only mobile check of the epic (twenty real-model sites, every page at 390 and 1440 in a browser) found six faults. * Taste

Ben, 2026-10-21, on the eighteen-site showcase: "These look stupid." Variety had become gimmicks: tilted cards, outline headlines, decorative circles, loud grounds, question headlines, "illustrative business" in body copy, and inner pages that were empty coloured boxes with letter chips.

** The taste block

The catalog's =taste= block (at the end of =catalog.yaml=) holds:

- =openings= and =variants=: gimmicks that never render on an unthemed site; a writer that names one gets the component's first calm variant.
- =chroma=: the page and surface colours of a light ground are calmed to this chroma; a neon accent (chroma over 0.35, HSL lightness over 0.45) is toned down, and ink, muted and accent-ink text are moved until AA passes.

The other values stay in the library for themes and explicit options only.

** Words

Visible copy never says "illustrative". Talk of stock photographs or visual references belongs only in =footer.note=. A customer's site never says its business is an example, invented or a demo, anywhere: =ls_taste_example()= finds such a line, and the plan and site checks refuse it. Only an explicit demo build (=site.demo: true= in the recipe, copied into the plan as =demo=) may say so, once, in =footer.note=. The plan and page checks refuse anything else, so the model retries with the reason. Each page's first heading, and the visual headline, is a statement: a question is refused.

** Photos on every page

** No photo twice on a page
