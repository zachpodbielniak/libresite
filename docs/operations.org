* Commands

=--unlimited= disables provider time and requested output budgets, overriding recipe values and =--timeout=. It is execution-only, so an unchanged old recipe can resume its checkpoint with unlimited budgets. Bundled recipes explicitly set =timeout: 0= and =max_tokens: 0= for testing. Prompt-size limits remain opt-in. Cancellation and finite retry counts still work; this setting does not bypass artifact validation. Provider-native model limits remain outside libresite's control.

Changing a bundled recipe's budget values changes its fingerprint. For the active Reading Room workspace, the original recipe was preserved as =example-site.libresite-work/recipe-before-unlimited.yaml=. Resume that checkpoint with:

#+begin_src bash
./build/debug/libresite -r ./example-site.libresite-work/recipe-before-unlimited.yaml -o ./example-site --resume --debug --unlimited
#+end_src

=--help= / =-h= provides examples. =--version= prints the release and =--license= prints the preserved license. =--list-modules= lists the eight built-in names. =--recipe FILE= / =-r FILE= selects the YAML recipe. =--output DIR= / =-o DIR= selects a new directory for generation; its parent must already exist.

=--validate= checks local schema, AI settings, registered module names, prompt/style resolution and native validation options without calling providers or creating output. =--plan= prints tab-separated index, id, type, provider and model; the display index starts at one. =--preview STEP-ID= shows the system and task prompt with the recipe's seed artifacts (empty when omitted), without simulating earlier steps. These three modes are mutually exclusive. Native validate steps have no AI prompt to preview. All positional arguments are errors.

=--prompts FILE= replaces the embedded catalog. =--plugin FILE= loads a native module and may be repeated. =--resume= permits reuse of an existing matching private workspace. Recipe and catalog paths are resolved from the CLI's working directory. There is no server process, deployment action or generated build execution inside this command.

* Provider setup

Authenticate each requested CLI using its own normal account setup before invoking a recipe. ai-glib reads provider-specific executable overrides: =CODEX_PATH=, =CLAUDE_CODE_PATH=, =GROK_PATH=, =CURSOR_AGENT_PATH= (or =CURSOR_PATH=), and =AGY_PATH=. These are useful for explicit installations and offline protocol tests. Model/effort settings are opaque identifiers interpreted by the adapter and installed CLI.

Every generation call creates a fresh temporary working directory, disables session persistence unless =--debug= is set, and sends the current project in the prompt. Permission bypass is enabled for every CLI adapter so the worker thread cannot stall on an approval prompt. Codex therefore uses =--dangerously-bypass-approvals-and-sandbox= rather than a read-only sandbox: Codex 0.153 =exec= does not accept =--ask-for-approval=, and read-only plus never-ask still waits for sandbox-escalation approval on the same stdin used for the prompt. Other CLI flags and defaults belong to ai-glib and the installed provider. A working directory is not a security sandbox. Use an external isolation boundary when stronger confinement is required.

Empty temporary provider directories are removed. Directories in which a third-party CLI created files are deliberately retained rather than recursively deleting unknown files. No global CLI configuration or credentials are modified by libresite.

* Debug tracing

Add =--debug= to generation or resume to enable provider-native session persistence and timestamped diagnostic metadata on stderr. For Codex this removes =--ephemeral=, allowing its normal session JSONL files to be written. Each attempt still starts a fresh provider session; libresite resume restores its own checkpoint, not a previous Codex conversation. The debug flag is independent of =DEBUG=1= compilation and does not change checkpoint fingerprints.

#+begin_src bash
./build/debug/libresite -r recipes/application.yaml -o ./example-site --resume --debug 2> ./libresite-debug.log
#+end_src

Before calling the provider, diagnostics report provider, requested model/effort (or provider defaults), timeout, token budget, system/task byte counts and the unique temporary working directory. Debug retains that directory even when empty. Match the logged =cwd= against Codex session metadata under its configured home (normally =~/.codex/sessions/=) to locate the live rollout. After the call returns, logs report elapsed milliseconds, session ID if the adapter extracted one, error domain/code, response byte count and stop reason. Normal attempt/retry/error messages remain enabled. The synchronous adapter buffers the event stream until completion, so a timeout may have no extracted session ID; matching the recorded cwd is the tracing path during a call.

Diagnostic metadata does not dump prompts, generated file contents or environment variables. Provider-persisted sessions can contain prompts and project contents. Session storage and retention belong to the installed provider; other adapters honor persistence according to their native capabilities. Debug does not globally enable dependency log domains. Remove retained temporary directories and provider sessions when finished tracing. An already running process must be stopped and restarted with =--resume --debug= to enable tracing.

* Checkpoints and publication

During generation, =OUTPUT.libresite-work/= is a private, owner-only directory. =lock= provides advisory process exclusion. =checkpoint.json= holds format version, the recipe/catalog fingerprint, next step index and all successful file contents. It also includes per-step usage and accounting completeness, and is replaced consistently and durably before execution and after each successful or failed step. See [[file:usage.org][usage accounting and pricing]]. Logs/progress go to stderr; redirect or tee stderr for a persistent human-readable run log. Checkpoint records and final metadata are structured machine records, not secrets storage.

A failure leaves the workspace available for inspection and resume. Re-run the same recipe and catalog with the same =--output= and =--resume=. If the recipe changes semantically or the catalog bytes change, resume fails instead of mixing incompatible generation. Comments/formatting changes in a recipe normally preserve its parsed fingerprint; mapping-order changes can alter it. Changing native plugin code/resources is not fingerprinted; start a new output for that case.

After the last step succeeds, files are exported to a fresh UUID-named directory inside the workspace. =.libresite/run.json= records the final checkpoint. A same-filesystem move publishes the directory only when the destination is absent. Interrupted exports remain inside the private workspace and are not resumed as trusted state. Successful workspaces are removed if empty; old failed export directories can keep a workspace around for inspection. Libresite never recursively removes an existing project.

Step progress lines include local wall-clock time with a numeric timezone offset, for example =[2026-09-09T14:32:05-0400] [1] brief: started=. Each start and checkpoint event captures its own timestamp. These lines remain on stderr so stdout can be used for plans and prompt previews.

Generation reports each attempt number, total attempts, provider and per-attempt timeout. A rejected attempt reports its error before retrying. Every 30 seconds the CLI prints elapsed waiting time and the latest status; this is a liveness indication from libresite, not provider token progress. Accepted artifact contents remain unchanged until the entire step succeeds; usage accounting also records failed executions. For example, =timeout: 900= with =retries: 1= permits two 15-minute provider calls for a single step. A fresh provider process partway through a long step can therefore be a retry rather than a hung timeout. Rebuild and restart with =--resume= to use new progress reporting; an already running process keeps its previous behavior.


* Generated repository publication

Every successful =--output DIR= publication includes =DIR/.git= and =DIR/.gitignore=, with a single commit on =master=: =chore: initial generated project=. Git must be on =PATH= (Fedora =git-core=). The initial commit uses =Libresite <libresite@localhost>= even when no personal Git identity is configured. Subsequent commits use your normal Git configuration. Libresite neither adds a remote nor pushes the project.

Existing generated ignore rules are retained. Baseline rules appended during export ignore =.libresite/= (which contains the full run checkpoint), private workspaces, =.env= and its local variants, build/distribution/coverage output, common dependency and language caches, object/shared/static libraries, logs, SQLite/database files and editor backups. Environment examples (=.env.example=, =.env.sample=, =.env.template=), dependency lockfiles and source files are eligible for tracking; project-specific ignore rules still apply. Ignored generated files remain on disk. Review stack-specific rules and secrets before sharing; this policy is not a content scanner.

Initialization, staging and committing all finish inside the private export before the directory move. Git errors (including a missing executable) prevent publication and preserve completed checkpoints. Correct the error and repeat the same command with =--resume=; this reconstructs a fresh export and repository without rerunning completed model steps. Failed exports remain available for inspection under the workspace. Inherited =GIT_*= environment settings, system/global Git configuration, templates, hooks and signing cannot redirect or block the automated commit.

* Cancellation and errors

=--timeout SECONDS= overrides every provider attempt's total deadline for this invocation, including step-specific recipe values. Omitting the option uses recipe settings; 0 disables the deadline, and positive values through 86400 set a deadline. The internal reset value -1 also selects recipe settings. This execution-only override does not mutate the parsed recipe or checkpoint fingerprint; it can recover an existing timed-out run. For example:

#+begin_src bash
./build/debug/libresite -r recipes/application.yaml -o ./example-site --resume --debug --timeout 3600
#+end_src

Deadlines apply even while the provider is receiving response tokens. Codex rollout files record completed items, so a long unfinished response can leave JSONL unchanged despite ongoing network reads. In the September 10 investigation, a ten-second syscall sample showed 315 receives and TCP receive counters continued growing while the rollout stayed unchanged. This establishes activity in the retry, not the semantic quality or eventual success of its answer. Do not treat heartbeat or rollout modification time as a token-progress meter.

The resolved =AI SETTINGS= object is sent in the task prompt so the catalog's configured-output-budget instruction has an actual value. The pinned Codex adapter ignores its =max_tokens= argument when constructing CLI arguments: for Codex the value is model guidance, not a hard output cap. Increasing the deadline allows a long response to finish but cannot guarantee model compliance or successful validation. No dependency pin, global provider configuration or completed checkpoint is changed by this recovery.

SIGINT/SIGTERM cancel the run through =GCancellable=. Cancelled calls are not retried. Completed checkpoints remain available. Exit status is 0 on success, 130 for a returned cancellation error, and 1 for other failures. Provider-specific timeout failures are errors and may be retried within the configured bound. No successful output is published when a provider fails or a required artifact is missing.

Errors report the failed stage ID where possible. Common remedies:

| Error | Resolution |
|-------+------------|
| Unknown key/type/style/prompt | Correct the recipe or catalog; load the required native plugin |
| CLI executable/authentication failure | Fix the provider's own installation/account setup |
| Truncated model output | Increase a supported output budget or split the stage |
| Invalid file-bundle JSON/path | Inspect the prompt; a bounded retry can ask the model to correct it |
| Existing output | Use a different output path; completed projects are not overwritten |
| Existing workspace | Resume matching work or choose a new output |
| Workspace locked | Wait for the active run; do not delete its lock inode |
| Checkpoint mismatch | Use the original recipe/catalog or start new work |
| Missing required artifact | An AI step immediately before validation retries the incomplete proposal within its configured retry budget; resume retries that AI step after exhaustion |

* Practical limits

Checkpoints produced before the acceptance-retry fix may already be parked at a failing native =validate= step. Repeating =--resume= alone cannot repair such a checkpoint because native validation makes no AI calls. Preserve a backup before any manual artifact repair, and retain the original catalog through =--prompts= if its embedded version has since changed. Do not lower acceptance requirements or reset a completed-step index merely to make a run appear successful.

YAML/catalog/checkpoint text: 16 MiB. YAML nesting: 32 collections. YAML events: 100,000. Recipe steps: 128. Generated file: 16 MiB. Project: 4096 files and 64 MiB of text. Generated paths: 1024 bytes with components at most 255 bytes. System plus task prompt: unlimited by default. Set =--max-prompt-bytes BYTES= to opt into a byte cap; =0= disables it. Explicit caps are checked before small bounded retry feedback. These are hard errors, not silent truncation.

The complete project is sent to each model. Libresite imposes no prompt byte ceiling by default; provider token windows, transport constraints and available memory still apply. An explicit cap rejects oversized requests with actual and allowed byte counts, without truncation. Change or remove the cap and resume the same output: it is an admission setting, not part of the recipe/catalog fingerprint. For large projects, design a native module with focused context or generate independent components as separate recipes; there is no automatic retrieval, summarization, binary asset pipeline or incremental editing of an existing output directory. Runtime build/test/browser verification belongs to the generated project and must be performed separately.

* Native content acceptance

Optional =validate.options.checks= enforce literal content and inclusive byte bounds before publication. Missing required text, forbidden text or out-of-range byte counts in a model response are retryable acceptance failures when native validation immediately follows generation. Whitespace-only required files also fail. =--validate= checks the entire predicate schema locally; =--preview= includes the exact rules in the generation prompt. See [[file:recipe-format.org][the recipe reference]] and [[file:../recipes/checked-landing.yaml][the checked landing recipe]]. These checks do not execute generated programs.

Inputs with quoted numeric/boolean/null values now retain their YAML string type. This corrects dependency scalar coercion; it can invalidate a checkpoint whose original recipe depended on that bug. Keep the original binary/catalog for recovering such existing work or generate into a fresh output with a corrected recipe. Existing shipped recipe and catalog bytes are unchanged by this review.

* Incremental revision

=--revise DIR= imports an existing text project and interprets =site.brief= as a change brief. It works with =--validate=, =--plan= and =--preview=; generation still requires a new =--output= outside the source tree. The revision result has its own Git repository and =feat: revise existing project= commit. Resume also verifies the current source snapshot. See [[file:revision.org][revision.org]] for commands, supported files and exclusions.
