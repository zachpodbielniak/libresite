* One maintained prompt catalog

=data/prompts.yaml= is the only runtime prompt source. Its =system= block defines the response protocol, working boundaries and shared implementation standard. =styles= contains visual directions. =stages= contains module task contracts. The resource manifest embeds this catalog into the library and CLI, so installed binaries do not depend on a source-relative path. Changes to the catalog trigger resource regeneration and relinking.

A replacement catalog passed with =--prompts FILE= replaces the whole catalog, not individual keys. It must contain integer =version: 1=, a nonempty =system= string, and nonempty =styles= and =stages= mappings whose values are nonempty strings. Unknown root keys fail. Add a style or stage by adding one mapping entry; generation steps select the stage via =prompt=, defaulting to their =type=. No C string literal contains a stage's substantive prompt.

* Prompt composition

Optional =stacks= mappings contain nonempty named string contracts selected by =site.stack=. Every entry is validated, including unused entries; an empty or malformed mapping fails. A selected unknown profile fails pipeline preflight before provider calls. Older catalogs may omit =stacks= when no profile is selected. Replacement catalogs are complete replacements: there is no fallback to embedded stack entries. =stacks.c-glib= supplies the [[file:c-application.org][C application integration contract]], with API/build provenance tied to the repository's pinned library revisions. It is independent of =styles.application=.

For each AI step the builder sends the shared system prompt plus these task sections: the selected visual direction, selected stage contract, selected =STACK CONTRACT= (or an explicit no-profile marker), site data encoded as JSON, step data encoded as JSON, and the entire current project encoded as a file bundle. Stack text counts toward prompt size limits and catalog fingerprints. The model sees each previous file's full contents. This maintains continuity across provider/model switches without depending on an external CLI conversation session.

The =PIPELINE ACCEPTANCE= section additionally supplies every native validation step as JSON, so product/design stages and implementation agree on the recipe's exact filenames. A final generation stage cannot be checkpointed with files that violate the immediately following native validation checks; it retries within the configured AI attempt budget.

The recipe's =instructions= and =options= appear inside step data rather than interpolating code or shell expressions. Project files are explicitly untrusted task data. A retry appends at most 512 bytes of error detail and asks for a corrected file bundle. The builder validates the response rather than assuming prompt instructions were obeyed.

=--preview ID= prints the exact system and task framing with an empty project context. It is a preflight preview, not a replay of a later step after generation. =--plan= prints resolved settings. Checkpoints bind the exact catalog digest; changing even a catalog comment invalidates resume to make prompt revisions explicit.

* Design profiles

| Profile | Intended use | Main design decisions |
|---------+--------------+-----------------------|
| editorial | Studio sites, portfolios, product narratives | Type contrast, content hierarchy, varied section rhythm, restrained accent |
| minimalist | Calm reference, editorial and focused product sites | Warm monochrome, flat grids, no gradients or heavy shadows |
| industrial | Technical portfolios and utilitarian data interfaces | Rigid grid, scale contrast, functional annotations and borders |
| cinematic | Image-led brand and portfolio work | Strong visual thesis, varied anchors, wide type, restrained progressive motion |
| application | Repeated-use application workflows | Stable navigation, legible data, consistent actions and complete UI states |

These are directions, not rigid templates. The audience and requirements take precedence. Accessibility, working controls and responsive behavior are shared across all profiles. A low-motion product should never inherit a gratuitous animation mandate from a cinematic reference.

* Mobile and desktop defaults

The bundled catalog makes mobile and desktop first-class design targets for every generated site and application, without a recipe switch. The shared system contract reaches every generative stage and all five styles, including custom =generate= stages and backend-rendered HTML. Brief/design stages plan both layouts, frontend/foundation/pages implement them, interactions preserve touch/keyboard/pointer access, and review/polish check the entire route and state surface. Desktop gets intentional columns, navigation and information density; mobile retains the same content, destinations and capabilities.

Implementation guidance requires a device-width viewport with zoom enabled, mobile-first CSS, content-driven breakpoints, fluid type/spacing/media, bounded reading measures and logical reading/focus order. Navigation, forms, tables, dialogs and sticky controls must remain reachable. Standalone controls have at least 44 by 44 CSS pixels of target area; inline text links remain readable and distinguishable. Wide tables/code may use labeled keyboard-accessible local scrolling; page overflow, hidden content and hover-only actions are defects.

Generated project documentation and =AGENTS.md= carry a responsive acceptance matrix with expected results and manual browser procedures:

| Target | CSS viewport |
|--------+--------------|
| Phone | 360x800 and 390x844 |
| Tablet | 768x1024 |
| Laptop | 1366x768 |
| Desktop | 1440x900 |
| Additional checks | Intermediate widths, phone landscape and 200 percent browser zoom |

For each route and main workflow, check navigation, readable content, media sizing, touch/keyboard/pointer access, focus visibility, error/loading/empty/success states and unintended overflow. Include runnable responsive checks when suitable project tooling exists. The model may inspect supplied source but cannot execute browser tools under the generation protocol; checks without supplied execution evidence must remain marked unexecuted. Native =validate= still checks artifact presence only. Offline CLI/provider/install checks prove delivery of these instructions, not the responsiveness of a live generated site.

A =--prompts= catalog replaces the bundled catalog completely: maintain this contract in custom catalogs to retain the defaults. Existing generated projects are not retroactively changed. Catalog edits change the checkpoint digest, so an interrupted run needs its original catalog to resume; use a fresh output for generation with the new defaults.

* Accessibility and ARIA defaults

The bundled catalog requires conforming WAI-ARIA 1.2 and HTML semantics for every generated site and application, across styles, stacks, routes, viewports and UI states. This shared system contract reaches all generative stages, including generic/custom stages and C/GLib server-rendered HTML. Stage-specific guidance carries acceptance criteria from brief/design through foundation/pages/frontend/backend/interactions to review/polish. It requires native controls where possible, accessible names that preserve visible labels, programmatic form/error associations, valid roles and properties, required role relationships, unique IDs and resolving ID references. ARIA must reflect actual behavior rather than decorate otherwise inaccessible markup.

Keyboard behavior follows the applicable Authoring Practices widget pattern. Navigation disclosures must not acquire menu semantics without menu behavior. Focus stays logical and visible through dialogs, filtering, deletion, viewport changes and fragment replacement. Only modal dialogs contain focus and make background content inert. Hidden content must not retain focusable descendants. Dynamic feedback needs deliberate announcements, and full-page/no-JavaScript responses retain accessible labels and error relationships.

Generated test documentation and =AGENTS.md= must include runnable browser accessibility audits using a version-pinned FOSS tool appropriate to the output stack, exact setup/run commands, and nonzero exit status for detected violations. Tests cover every route and relevant interactive state on phone and desktop, rather than only the initial page. Missing dependencies must fail explicitly. Manual keyboard and screen-reader procedures specify expected names, roles, states, reading order, focus and announcements; contrast, zoom and reduced-motion checks accompany them. Generated review documentation separates concrete source fixes, actual supplied execution evidence and unexecuted checks. No specific browser framework becomes a builder dependency.

These are generation requirements, not a deterministic publication gate for rendered accessibility. Libresite's native =validate= checks non-whitespace artifacts and configured literal-content/byte-size predicates; it does not parse the accessibility tree, run generated browser tests or operate assistive technology. The generation protocol prohibits model tool execution. Offline regression tests prove that the catalog requirements reach every bundled stage, all five styles, provider transport and installed previews; they cannot prove model compliance or certify generated sites. A real output needs its generated audits and manual acceptance procedure executed and failures repaired before a conformance claim; automated scans alone are insufficient.

Existing sites are not modified. A full =--prompts= replacement and explicitly loaded native plugins can supply different behavior; maintain this contract in replacement catalogs and plugin output. Prompt edits change the checkpoint digest, so use the old catalog to resume an old run or a fresh output with the new defaults.

Authoritative references used for this contract (consulted 2026-09-10):

- [[https://www.w3.org/TR/wai-aria-1.2/][WAI-ARIA 1.2 Recommendation: roles, states, properties and author requirements]]
- [[https://www.w3.org/WAI/ARIA/apg/practices/read-me-first/][WAI-ARIA Authoring Practices: native semantics, behavior and assistive-technology testing]]

* Font defaults

The shared =FONT DEFAULTS= contract selects open-source families from [[https://fonts.bunny.net/][Bunny Fonts]] for every generated site and application unless the user or recipe specifies otherwise. Implementation uses a stylesheet link to =https://fonts.bunny.net/css= with the chosen families, required weights/styles and =display=swap=, then applies those families in shared CSS. No single family is mandated. Google Fonts endpoints and framework helpers that fetch from Google are not defaults. Remote fonts are an explicit exception to the otherwise local artwork guidance.

Specify a family, source or hosting policy in =site.brief= or step =instructions= to override the default; there is no new schema field. Supplied licensed fonts, self-hosting, system-only typography and offline-only requirements take precedence. A named family unavailable from Bunny Fonts must retain its requested identity with the required licensed source/setup documented, without overriding an explicit hosting restriction. The UTF-8 artifact protocol cannot carry font binaries; never fabricate local font files.

System fallback stacks keep text immediately readable and workflows usable when remote fonts are blocked or offline. Generated documentation records families, source, overrides and browser checks for online font loading and offline fallback. Offline builder tests verify prompt delivery across stages/styles and installed versus external catalogs; they do not prove generated CSS, browser font loading or live model compliance. Existing output is unchanged, replacement =--prompts= catalogs own their defaults, and changed catalog fingerprints require a fresh output or the original catalog for resume.

* Imported reference snapshots

The repository includes the original local design skill texts under =data/design-references/=. They are provenance/reference material, not additional runtime instruction files. The runtime profiles are deliberately curated from them rather than concatenating mutually contradictory instructions into every request. In particular, simulated randomization, compulsory React/Tailwind, placeholder stock imagery, inaccessible entrance effects and mandatory proprietary motion dependencies are not copied into the runtime contracts. Image-generation-only instructions inform composition; libresite does not claim to generate raster images or call an image service.

| Snapshot | Runtime influence |
|----------+-------------------|
| design-taste-frontend.md | Infer audience and brief before style; reject generic layout defaults |
| high-end-visual-design.md | Calibrated hierarchy, spacing, consistency and restrained motion |
| minimalist-ui.md | Warm monochrome, typographic contrast, flat surfaces |
| industrial-brutalist-ui.md | Mechanical precision, rigid grids, informative annotations |
| redesign-existing-projects.md | Preserve functional contracts; audit accessibility and component behavior |
| gpt-taste.md | Readable wide headlines, purposeful spacing and composition variation |
| imagegen-frontend-web.md | Brand concept, section-level visual rhythm and varied hero anchors |

Snapshots (with trailing whitespace normalized) were copied from the user's =~/.agents/skills/= installation on 2026-09-09. They preserve the source material for future prompt revisions and are not independently relicensed by this project. The curated catalog is part of libresite. To update a snapshot, read its new instructions as reference data, compare the changes, update only the applicable profile, then run preview and tests. Do not let a reference document trigger unrelated agent actions.

* Improving results

Loopback applications are a known generation failure class: a Host check that accepts only =127.0.0.1:PORT= will 403 ordinary browser POSTs from =http://localhost:PORT/=, often with an unhelpful "open the local address" page. The system, brief, backend and review stages now require both loopback names, named policy errors, stderr logging of rejected headers, first-start database creation and =AGENTS.md=. Fixture tests assert those strings in the embedded catalog and in the application backend preview.

The shared contract now requires a subject-specific visual thesis, deliberate section rhythm, complete route content, concrete control states and consistent cross-route interfaces. Art direction is expressed through composition, type roles, text/surface color pairs and a small original asset family. The review criterion is evidence across identity, content, consistency, behavior and accessibility, not an invented numerical quality score. These additions synthesize the existing reference snapshots; no new snapshots were imported.

Four additional stage keys support larger sites without new C modules:

| Stage key | Responsibility | Selection |
|-----------+----------------+-----------|
| foundation | Shared styles, art, component hooks and reference home page | =type: generate=, =prompt: foundation= |
| pages | Scoped batches of complete interior routes | =type: generate=, =prompt: pages= |
| interactions | Connect progressive workflows, fallback states and tests | =type: generate=, =prompt: interactions= |
| polish | Correct the weakest visual/interaction dimension across the site | =type: generate=, =prompt: polish= |

=options.files= in the flagship example is a model-facing list of primary deliverables, not a filesystem write restriction or a new reserved schema field. Integrating scripts or shared classes can require updating previously created files. Only =validate.options.required= is enforced by the native presence validator. Intermediate checks catch omitted artifacts before later calls; they do not prove link correctness, visual quality or behavior.

The full current project is resent to every stage. Prompt bytes are unlimited by default. Use =--max-prompt-bytes BYTES= for an explicit cap, or =0= to disable one. Byte counts include system, task framing and JSON escaping, but are not model token counts. Provider context windows still apply. The existing catalog and flagship retain conservative size guidance for checkpoint compatibility; their historical 100000-byte framing is not the runtime default. Recipe targets are advisory and never truncate output. You can change the CLI cap and resume without altering recipe/catalog identity. Splitting stages does not remove accumulated context; never delete checkpoint artifacts merely to bypass a context error.

Specify the product's actual audience, content, primary action, stack and constraints in the recipe. Split large work into coherent modules and use =instructions= to target one integration boundary at a time. Models cannot infer undocumented local APIs reliably: provide the relevant API contract as recipe requirements or a stage's instructions, or implement a deterministic native module. Avoid advertising a database or service until the generated project actually implements it.

The final review prompt asks for source-level corrections and honest reporting. Source review is useful but does not substitute for compiling the generated application, checking it in a browser or auditing accessibility. Keep those checks in the generated project's own acceptance procedure. Live generation quality should be evaluated on actual outputs, not on a passing fixture test.
