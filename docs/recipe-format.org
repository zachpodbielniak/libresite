* Contract

A recipe is exactly one UTF-8 YAML document with scalar string mapping keys. Unknown structural keys fail. Duplicate keys, aliases, anchors, explicit tags, complex keys and more than 32 nested collections are rejected. Input is limited to 16 MiB and 100,000 parser events. Use literal YAML blocks for long prose. Empty strings are not valid settings. No shell expansion, environment expansion, template evaluation or recipe command execution occurs.

#+begin_src yaml
version: 1
name: example
site:
  brief: Build an accessible static site for a small open-source project.
  audience: Developers evaluating the project.
  style: editorial
  frontend: Semantic HTML and native CSS.
  backend: none
  database: none
  requirements: Local assets, no tracking, working keyboard navigation.
ai:
  provider: codex
  timeout: 600
  retries: 1
  max_tokens: 16384
pipeline:
  steps:
    - id: product
      type: brief
    - id: design
      type: design
    - id: frontend
      type: frontend
    - id: review
      type: review
    - id: verify
      type: validate
      options:
        required: [index.html, README.org]
#+end_src

* Top-level fields

| Key | Required | Type | Meaning |
|-----+----------+------+---------|
| version | yes | integer | Exactly 1; quoted "1" is not an integer |
| name | yes | nonempty string | Human-readable project identity |
| site | yes | mapping | Product and stack brief |
| ai | no | mapping | Default AI settings |
| seed_artifacts | no | sequence | Initial UTF-8 files, each with exactly path and content |
| package | no | mapping | Sold SKU identity: sku, release and kind; see below |
| pipeline | yes | mapping | Exactly one key, steps |

=package= has exactly =sku= (1..64 lowercase letters/digits/hyphens starting with a letter), =release= (string numeric major.minor.patch) and =kind= (=site= or =application=). A site package has no selected stack; an application package requires =site.stack: c-glib=. The =application= SKU cannot be relabeled as a site. Every package must end with a native =validate= step and a nonempty =options.checks= array; ordinary validator preflight checks the full predicate schema. This optional metadata is part of the recipe fingerprint. Existing recipes without it remain valid and retain their identity. =version: 1= is still the schema version. See [[file:packages.org][sold packages]] for fixed scopes, acceptance, =--seal-package=, =--package= and archive retention.

=site= accepts structured =pages=, =offers=, =contact=, =brand=, =copy_lock= and =languages= plus optional =brief=, =audience=, =style=, =stack=, =frontend=, =backend=, =database= and =requirements= strings. All six structured fields are required when the legacy =brief= is absent; see [[file:structured-recipes.org][the complete field schema and form-to-YAML API]]. All present string settings must be nonempty. YAML =none= is text, while =null= is not. =style= defaults to =editorial= and must exist in the selected prompt catalog. Optional =stack= selects a named =stacks= entry in that catalog; an unknown name fails preflight. No stack profile is selected implicitly. The bundled =c-glib= profile supplies yaml-glib configuration, htmx-glib pages and orm-glib persistence with SQLite by default; see [[file:c-application.org][C applications]]. It is independent of visual style. The =frontend=, =backend= and =database= strings remain open-ended instructions, not a finite list of compiled backends. The builder emits source projects; it does not link every generated site's runtime into itself.

=pipeline.steps= is an ordered sequence of 1 through 128 mappings. A step runs only after all preceding steps have succeeded and checkpointed. There is no implicit parallelism, conditional execution or hidden dependency graph.

* Seed artifacts

Supply client copy, logo SVG, brand YAML and approved legal text through =seed_artifacts= before generation. Each entry contains exactly a safe relative output =path= and literal string =content=. Content is included verbatim in the initial artifact context; no host files are read and no source-path or command expansion occurs. Embed existing text using YAML literal blocks. Omitted seeds and an empty sequence both start with an empty project.

#+begin_src yaml
seed_artifacts:
  - path: content/client.org
    content: |
      #+title: Approved client copy
      Independent tools for independent people.
  - path: assets/logo.svg
    content: |
      <svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 32 32"><path d="M4 4h8v16h16v8H4z"/></svg>
  - path: brand.yaml
    content: |
      name: Example
      colors:
        ink: '#202020'
        paper: '#faf8f4'
  - path: legal/terms.txt
    content: |
      Insert the client's approved legal text here before generation.
#+end_src

Seed validation uses the same transaction, path, type, duplicate, file/directory conflict and resource-limit checks as provider bundles. The entire recipe, including seeds, remains subject to the 16 MiB YAML document limit. Invalid seeds fail recipe loading before provider calls or workspace creation. Seeds must be UTF-8 text, including SVG; binary assets are not supported. Quote scalar-looking contents such as ='123'= or use literal blocks to retain their string type.

Seeds populate =CURRENT PROJECT= in =--preview= and preflight, and are saved in checkpoint zero before the first pipeline step, including a native step. A preview contains seeds only; it does not simulate earlier generation steps. Seeds remain in subsequent prompts and exports unless a step replaces their exact paths. They are initial inputs, not immutable or protected files: use step instructions and native literal-content checks for preservation requirements. Only supply content intended to be sent to the selected AI provider and included in the output project.

Resume restores the accepted checkpoint without reapplying seeds, preserving later replacements. Seed paths and content are part of recipe identity; changing them invalidates a saved checkpoint. Recipes without =seed_artifacts= retain their existing checkpoint identity. Embedders can call =ls_recipe_create_context()= for a seeded preview or initial context when executing steps directly.

* Steps

| Key | Required | Type | Meaning |
|-----+----------+------+---------|
| id | yes | nonempty unique string | Progress and checkpoint identity |
| type | yes | nonempty string | Registered module name |
| prompt | no | nonempty string | Catalog stage key; defaults to type for generation modules |
| instructions | no | nonempty string | Specific task refinement included as step data |
| ai | no | mapping | Settings overriding pipeline AI defaults |
| options | no | mapping | Module-specific data; passed intact to the module and generation prompt |

Built-in AI module names are =brief=, =design=, =frontend=, =backend=, =database=, =review= and =generate=. These all use =LsGenerateStep= with different centralized stage contracts. =generate= is the general-purpose extension for instructions that need no custom C implementation. A custom =prompt= can reuse any catalog stage or a stage added to a replacement catalog.

The native =validate= module calls no provider. It requires =options.required=, a nonempty sequence of unique safe relative file paths, and checks every named artifact for non-whitespace text. Optional =options.checks= adds literal-content and byte-size predicates as described below. These checks do not prove HTML correctness, accessibility, compilation or working application behavior. Unknown native validation options fail before any AI calls. Add semantic checks as separate registered steps when needed.

Generated sites must include =AGENTS.md= so a later coding agent can maintain and troubleshoot the output. Bundled recipes require that path in the final =validate= step. The file is Markdown on purpose: it is an agent instruction file, not project documentation. Project docs remain Org. For a loopback application, =AGENTS.md= and =README.org= must document both =127.0.0.1= and =localhost= as accepted Host/Origin names on the listening port.

For a generation step, =options= is open-ended task data understood by the model; it is not an executable instruction language. For a plugin, its author defines and validates =options=. A native plugin can use the same artifact store as built-in generation.

* SEO output contracts

SEO is enabled through the shared prompt catalog, with no new recipe keys. Supply a known production HTTPS URL, language requirements and privacy constraints through =site.requirements=. Every bundled final validator requires =config/seo.yaml=, =docs/seo.org= and =tests/seo.sh=; static recipes additionally require =robots.txt= and =scripts/prepare-seo.sh=. Include these paths when authoring equivalent custom recipes. A sitemap is produced only for a configured public output, so the domain-free bundled recipes do not require a source =sitemap.xml= full of invented URLs. The checked landing's literal homepage checks apply to its noindex preview; adapt them when supplying public deployment facts. See [[file:seo.org][SEO configuration and verification limits]].

* AI settings

| Key | Default | Accepted value |
|-----+---------+----------------|
| provider | codex | codex, claude-code, grok-build, cursor, antigravity |
| model | provider's default | Nonempty opaque model identifier |
| effort | provider's default | Nonempty effort identifier passed to ai-glib |
| timeout | 600 | Integer seconds, 0 through 86400; 0 disables the deadline |
| retries | 1 | Integer additional attempts, 0 through 5 |
| max_tokens | 16384 | 0 for unlimited, otherwise integer requested output budget 256 through 131072 |

Settings are resolved independently for every step. Changing provider drops an inherited =model= and =effort= unless the step explicitly sets them; this prevents accidentally sending a Codex model to Claude. Other defaults remain inherited. An unchanged provider inherits the model and effort normally. =--plan= prints the result without contacting providers.

Not all CLIs implement every budget or effort knob; ai-glib translates what the chosen adapter supports. Unknown model/effort identifiers are not remotely validated by =--validate=. Provider authentication and installed CLI compatibility remain runtime requirements.

A failed provider call or invalid artifact bundle is retried up to =retries= times. Corrective feedback describes the rejected response. There is no retry after cancellation. Every attempt may consume provider usage; keep retries explicit for expensive pipelines.

Every generation prompt includes the recipe's native validation contracts, including exact required filenames. A generation step immediately followed by one or more =validate= steps checks its proposed project against those contracts before accepting or checkpointing the response. Missing/empty required artifacts trigger the same bounded retry with corrective feedback. Failed candidates do not change the current project. Earlier planning steps are allowed to produce an incomplete project, and the native validation steps still run normally afterward. If attempts are exhausted, resume retries the failed AI step from the last successful checkpoint.

* Artifact protocol

Provider results are JSON because they carry exact file contents that may themselves contain YAML, markup or source code. This is a transport format, while user-authored recipes and prompts remain YAML.

#+begin_example
{"files":[{"path":"index.html","content":"<!doctype html>..."}],"summary":"Implemented the homepage"}
#+end_example

Only =files= and optional string =summary= are allowed. Every file contains exactly =path= and =content=. Full replacement text is required; omitted files remain unchanged. A bundle is validated completely before applying any replacements. Duplicate paths, traversal, absolute paths, backslashes, colons, control characters, reserved =.git= / =.libresite= path components and file/directory conflicts are errors. File content is UTF-8. Binary assets should be supplied outside this protocol; generated vector artwork can be SVG text. The current version has no file deletion operation.

Duplicate JSON members, embedded NUL escapes and JSON nesting beyond 32 collections are also rejected. Empty bundles are permitted for no-change review steps, but a complete pipeline that produces no files fails. Each file is limited to 16 MiB; the project to 64 MiB and 4096 files. The smaller prompt and checkpoint limits described in [[file:operations.org][operations.org]] usually constrain practical project size first.

* Deterministic artifact checks

Client-supplied sentences and phone numbers should be copy-locked with =contains= rules on their intended artifacts; see [[file:copy-lock.org][copy-lock authoring, retry behavior and delivery review]] and [[file:../recipes/copy-locked-landing.yaml][the complete example]].

Native =validate= steps accept optional =options.checks= alongside the mandatory =required= array. Required files must contain at least one non-whitespace Unicode character. All path lists reject duplicates. Each check applies to one exact safe relative path; the file must exist even if it is not listed in =required=.

#+begin_src yaml
options:
  required: [index.html, styles.css, README.org, AGENTS.md]
  checks:
    - path: index.html
      contains: ['lang="en"', 'name="viewport"', '<main']
      excludes: ['TODO', 'Lorem ipsum']
      min_bytes: 512
      max_bytes: 131072
    - path: styles.css
      contains: [':focus-visible', 'prefers-reduced-motion']
#+end_src

=contains= requires every listed literal string; =excludes= rejects any listed literal string. Matching is case-sensitive and does not interpret regular expressions, HTML or CSS. Each supplied list must contain 1..4096 unique nonempty strings. =min_bytes= and =max_bytes= are inclusive UTF-8 byte counts, not character counts; both are optional integers between 0 and 16777216, and a supplied minimum cannot exceed the maximum. A checked file may be empty when the predicates permit it and it is not also required. Checks are limited to 4096 unique paths and each rule must provide at least one predicate. Unknown keys and malformed rules fail local preflight before provider calls.

The complete validation configuration is already included in =PIPELINE ACCEPTANCE= prompt data. Consecutive native checks immediately after a generation stage run against its candidate before acceptance. A failed predicate triggers corrective feedback and bounded retry; an exhausted stage leaves the last successful checkpoint intact, so =--resume= runs generation again. Diagnostics identify the artifact and predicate index without printing file contents. [[file:../recipes/checked-landing.yaml][checked-landing.yaml]] demonstrates these rules with a standalone static recipe. Literal checks are useful for exact delivery contracts but cannot prove semantic correctness, accessibility or design quality.

Quoted and block YAML scalars preserve string types: ='1'= is a string and is rejected for byte counts; plain =1= is an integer. The boundary restores explicit string styles after yaml-glib conversion, including empty and null-looking strings. Existing recipes without formerly misinterpreted quoted scalars retain their parsed checkpoint identity. Recipes that relied on the previous incorrect scalar coercion need corrected input and a fresh output directory.

* Revision recipes and file operations

With CLI =--revise DIR=, =site.brief= describes the changes to the imported project. No additional YAML source-path key is needed. Use =type: generate= with =prompt: revision= for a focused edit stage, then native acceptance checks appropriate to the existing application. All generation stages receive the revision contract. See [[file:revision.org][revision.org]] and =recipes/revision.yaml=.

The response object additionally permits =delete=, an array of unique existing file paths. Keep =files= present, even when empty. Deletions and replacements cannot name the same path, and the whole transaction must satisfy path, size and structural constraints. File objects may include boolean =executable=; omission preserves an existing file's executable intent. Checkpoint snapshots contain final files rather than operations.
