* Workflow

A platform collects structured fields and submits a JSON form object to =ls_recipe_from_form()=, then saves =ls_recipe_to_yaml()= as the durable recipe. No AI call, generated prose, shell interpolation or network access is needed to create the recipe. The CLI adapter offers the same path and additionally runs catalog/module preflight before printing any YAML. Libresite supplies the data contract and adapter; the embedding platform owns its form UI and persistence.

#+begin_src bash
libresite --from-form form.json > site.yaml
libresite -r site.yaml --validate
libresite -r site.yaml --preview design
libresite -r site.yaml -o ./new-site
#+end_src

The form's top-level fields are =name=, =site= and optional =ai= and =pipeline=. They have the same meanings and types as a full recipe, except that =version= is supplied by the adapter and =site.brief= is rejected. Unknown fields fail rather than disappearing. The platform can use text controls for strings, repeatable rows for pages/offers, a repeatable exact-text control for copy locks, and a language selector with a default choice. Omit unfilled optional strings; do not send empty strings or nulls. No web server or GUI dependency is added to the builder.

If =pipeline= is absent, the adapter supplies product, design, frontend, review and native acceptance stages for a static site. Acceptance requires =index.html=, =README.org=, =AGENTS.md=, =config/seo.yaml=, =docs/seo.org=, =tests/seo.sh=, =robots.txt= and =scripts/prepare-seo.sh=. For applications or specific artifact layouts, supply a complete pipeline and its exact required output paths. AI settings retain ordinary recipe defaults unless explicitly supplied; form conversion itself never invokes a provider.

* Site fields

A structured site requires all six fields below. =offers: []=, =contact: {}= and =copy_lock: []= are valid explicit absence. Optional existing =audience=, =style=, =stack=, =frontend=, =backend=, =database= and =requirements= strings remain available. See [[file:../recipes/structured.yaml][the complete structured example]].

| Field | Form value and validation |
|-------+---------------------------|
| pages | 1..128 records: required unique =path= and =title= strings; optional =purpose= string and ordered =sections= list of 1..4096 unique strings |
| offers | 0..128 records: required unique =id= and =name= strings; optional =description=, =price=, =cta_label= and =cta_url= strings; CTA label and URL must occur together |
| contact | Mapping of optional =email=, =phone=, =address= and =url= strings; empty means no contact facts supplied |
| brand | Required =name= string; optional =tagline=, =tone=, =colors=, =fonts= and =logo= strings; logo is a supplied asset reference |
| copy_lock | 0..4096 unique nonempty exact strings; multiline text and leading/trailing whitespace are preserved |
| languages | Required =default= string and =supported= list of 1..4096 unique language tags; default must match an entry exactly |

Page paths are local URL paths starting with =/=, including directory routes such as =/services/=. Traversal segments, repeated slashes, whitespace/control characters, backslashes, percent escapes, query strings and fragments are rejected. Paths are routing requirements, not guaranteed output filenames; static directory paths can map to =services/index.html= while backend applications can dispatch routes. Use native =validate= artifact checks for exact file requirements.

Language tags use a 2..8 ASCII-letter first subtag followed by optional 1..8 ASCII alphanumeric subtags, for example =en=, =fr-CA= or =zh-Hant=. Case-only duplicates fail. This is a practical syntax check, not registry validation or complete BCP 47 support. Contact and offer values remain supplied text: parsing does not prove an address exists, a URL responds, a logo is available or a payment service works. Price and phone fields must be strings, including when all their characters are digits.

* Copy, brand and language behavior

Every generation stage receives the structured site intact as task data. The bundled prompt contract requires every page and language, preserves offer identities and supplied contact facts, applies explicit brand choices ahead of style defaults, and forbids invented missing business facts. Copy locks must appear as exact visible text, escaped appropriately for the target markup, without paraphrasing or translation. A lock retains its supplied language even on translated pages. Conflicts must be recorded in generated review documentation.

Recipe validation and YAML round-trip tests prove input structure and preservation, not model compliance. Native artifact checks can assert literal source text at known paths but do not establish rendered-text equality, complete translations or functioning contacts. Generated review documentation must carry the per-page/offer/contact/brand/copy/language checklist. Browser and content review remain necessary for those output guarantees. Replacement prompt catalogs must preserve this contract themselves.

For deterministic source acceptance, pair =site.copy_lock= with =pipeline.steps[].options.checks[].contains= on the intended artifact paths, as the structured example does for its homepage tagline. See [[file:copy-lock.org][literal copy checks and retries]]. The form adapter cannot infer placement or source escaping from visible strings alone and does not silently manufacture these predicates; supply the pipeline when those delivery checks are required.

* Library integration and round trips

=ls_recipe_from_form(const gchar *json, GError **error)= validates the bounded strict JSON transport, supplies defaults and returns an owned =LsRecipe=. =ls_recipe_to_yaml(LsRecipe *recipe, GError **error)= returns owned YAML text. Use =g_autoptr(LsRecipe)= and =g_autofree gchar *=; failures return NULL with an error. Call =ls_pipeline_validate()= against the chosen catalog/plugins before accepting platform submissions if custom styles, stacks or pipeline modules are exposed. The library constructor performs structural validation, while the CLI performs both layers.

=libresite -r existing.yaml --emit-yaml= re-emits an existing recipe without generation. Scalar strings are explicitly quoted so ="null"=, ="true"=, leading-zero phone numbers and prices do not change types in YAML consumers. Copy text is not trimmed or normalized. Execution-only timeout/unlimited overrides are not serialized. Re-parsing emitted YAML preserves the recipe tree and therefore its recipe contribution to checkpoint identity; changing structured fields correctly changes that identity.

* Legacy migration

Existing version 1 recipes using =site.brief= remain accepted with unchanged parsed trees. New structured recipes omit it. A legacy recipe can add structured fields incrementally; each supplied field is validated, and the bundled prompts give structured facts precedence where they conflict with prose. Removing =brief= requires all six structured fields. The form adapter always requires the complete structured contract and rejects prose input. Existing sample recipes remain compatibility examples; use =structured.yaml= for new platform integrations.
