* Generated Git repository checks

The offline CLI fixtures verify that each adapter publishes a clean committed repository. The installed native plugin test verifies the requested repository root, =master= branch, one Conventional Commit, preserved ignore rules, tracked source/lock/example files, and excluded secrets, metadata and build output. It also exercises conflicting inherited Git repository pointers, signing/hooks/template/exclude configuration, and failures during init/add/commit, missing Git, and cancellation during Git publication followed by checkpoint resume. These checks exercise real Git with controlled artifacts; they do not establish live AI design quality or generated application build/browser correctness.

* Run checks

Bundled live-testing recipes disable provider time/output budgets. Offline fixtures keep short deadlines deliberately to test timeout handling. The recovery regression resumes a finite-deadline checkpoint with =--unlimited= and verifies that it overrides a conflicting finite CLI deadline, returns a delayed fixture successfully, and renders both budgets as unlimited. SIGTERM cancellation is exercised with =--timeout 0=.

#+begin_src bash
make tests
bash tests/verify.sh
bash tests/install.sh
make DEBUG=1 ASAN=1 UBSAN=1 tests
#+end_src

=make tests= compiles and runs the GTest executables with fatal GLib warnings, then CLI integration tests. =verify.sh= runs clean parallel release and debug builds/tests, rejects warning/error diagnostics and runs ShellCheck. It checks its warning detector against a known positive control first. =install.sh= stages installation under a new temporary directory, runs the installed CLI outside the checkout, compiles and loads an external step plugin against installed headers, and runs a shared-library consumer. Temporary fixture directories are owned by the test that creates and removes them.

* Coverage

GTest covers valid recipes, wrong types, unknown keys, duplicate YAML keys, document/alias/tag rejection, invalid scalar settings, malformed catalog replacements, unknown prompt/style/module preflight, JSON duplicate/NUL/nesting rejection, duplicate step IDs, per-provider default isolation, safe paths, immutable boxed copies, atomic bundle rejection, replacements, file/directory collisions, complete publication, stage signals, per-step model changes, resume after interruption, corrupt/mismatched checkpoints, cancellation, existing outputs, symlinked workspaces, workspace locks, registration contracts, malformed-output retry, prompt size limits, and the bundled application loopback/AGENTS.md generation contract.

The injected provider replaces only model transport; the real recipe parser, prompt renderer, step engine, artifact store, checkpointing and filesystem publication run end to end. This avoids vacuous tests that merely assert that a mock was called.

Progress regression coverage forces a provider deadline and verifies that the retry reason and exactly two attempt announcements reach CLI stderr. A separate blocked-provider run waits for the real 30-second heartbeat, cancels with SIGTERM, and compares checkpoint bytes before and after waiting/cancellation. Each CLI suite therefore takes at least 30 seconds and exercises the worker/main-context boundary without a live account.

Debug tests verify that Codex defaults to =--ephemeral=, that =--debug= removes that flag even when resuming a non-debug checkpoint, and that diagnostics include request sizes, retained working directory, parsed fixture session ID, response metadata and timeout error codes. They check that diagnostic metadata stays on stderr without dumping fixture contents. Actual provider session file creation requires a live provider and is not simulated as evidence of live tracing.

CLI integration tests use actual =LsAiProvider= and ai-glib adapters with controlled executable fixtures for Codex, Claude Code, Grok Build, Cursor and Antigravity. They check file publication, model forwarding, unattended permission-bypass flags, output conflict handling, nonzero subprocess exit, resume, process deadlines and actual SIGTERM cancellation. No provider credentials, model calls or network access are required. Fixtures emit provider-specific envelopes; Antigravity success status is uppercase =SUCCESS=. Codex argv must include =--dangerously-bypass-approvals-and-sandbox= and must not include =--sandbox=.

* Accessibility contract coverage

CLI previews assert the shared accessibility/ARIA contract for every generative step of every bundled recipe, and the controlled Codex transport checks that it reaches provider stdin. Installed previews run outside the checkout and compare embedded versus installed replacement catalogs for all five styles using a generic =generate= stage. They check native semantics, accessible names, valid roles and relationships, ID references, state synchronization, hidden-focus rules, keyboard/focus handling, dynamic announcements, runnable browser audits and manual screen-reader procedures. These tests detect missing prompt delivery; fixture markup is not an accessibility-compliant reference site.

For an actual generated project, execute its browser audit across routes and interactive states, then perform the documented keyboard and screen-reader checks and repair findings. Missing test dependencies and unexecuted checks must be explicit. Neither prompt assertions, source-level native validation nor automated browser scans alone establish conformance. See [[file:prompts.org::*Accessibility and ARIA defaults][the generation contract]] for scope and replacement-catalog limits.

* What passing tests do not prove

Acceptance regression tests exercise syntactically valid provider bundles that omit required files: retry success, exhaustion with the original project intact, and no leakage of files from rejected attempts. Transport fixtures also assert that validation contracts are present in generation prompts.

Fixture success establishes the builder's deterministic behavior and its use of ai-glib protocol surfaces. It does not prove that every installed CLI version accepts the same flags, that a particular account has access to an example model, or that a live model will obey a prompt. This implementation has not been evaluated by paying for live generation across all five providers.

The generated site's =validate= stage checks required non-whitespace text and any configured literal-content and byte-size predicates. It is not a compiler, browser, HTML validator or accessibility checker. For a live acceptance run, create a new output with an authenticated provider, read its README, AGENTS.md and review report, compile/test its application, submit the primary form from both =http://127.0.0.1:PORT/= and =http://localhost:PORT/=, inspect narrow and wide viewports, follow the main workflow and verify keyboard/error states. Record actual evidence separately from model claims.

GTest =/prompt/application-contracts= and CLI preview checks pin the loopback Host/Origin, =AGENTS.md= and first-start database instructions in the embedded catalog and =recipes/application.yaml=. They do not compile a generated application. A generated project's own HTTP tests must POST successfully with =Host: localhost:PORT=.

* Adding tests

Deadline recovery tests first time out a controlled provider under the recipe's two-second limit, then resume that exact checkpoint with a ten-second execution override and a three-second response. Success proves the override reaches the transport and does not invalidate existing work. Prompt assertions verify the resolved timeout and output budget are visible to the model. Negative CLI checks reject invalid deadlines. These tests do not establish a live model's generation time or output quality.

Add new cases when they measure a real failure boundary. A new native step needs successful output plus invalid configuration, failure and cancellation cases. A new artifact operation needs transaction and path-conflict cases. A new provider should have a fixture exercising its real subprocess protocol and a documented optional live check. Keep tests offline by default and never silently skip required dependencies. Never lower warnings to make a test pass.

* Artifact contract regression suite

=tests/test-contracts.c= adds public-boundary tests for callback failures without errors, success with errors, post-callback cancellation and ignored diagnostics. Input tests cover strict JSON syntax, rootless input, allowlist-delimiter bypasses, quoted/block YAML string preservation and malformed native predicate schemas. Artifact checks exercise exact inclusive UTF-8 byte bounds, literal inclusion/exclusion, whitespace rejection, transactional corrective retries and retry exhaustion followed by checkpoint resume. The second GTest executable is part of =make tests= and therefore release/debug and sanitizer verification. Controlled CLI adapters and the installed native plugin also execute content predicates.

Native validation now proves required non-whitespace text plus any configured exact-content and byte predicates. It still does not prove a generated application build, browser behavior, accessibility or live design quality.

Installed plugin regression tests also reject registration success accompanied by an error and registration failure without a diagnostic. Both cases must stop local preflight and produce a useful error.

* SEO generation contracts

The =/seo/= GTest cases load each bundled recipe's actual final validator, require its SEO paths and check a positive literal-text fixture followed by missing, empty and whitespace-only variants of every SEO artifact. CLI previews cover each bundled generative stage, and the controlled Codex adapter confirms the shared SEO contract reaches its real subprocess input. Installed tests check every visual style with a generic =generate= stage from outside the checkout and compare embedded versus installed external catalogs. These checks do not call a live provider or execute generated SEO preparation/HTTP/browser tests. See [[file:seo.org][the SEO guide]] for generated-project acceptance responsibilities.

* C application generation contracts

=/prompt/stack-profiles= covers opt-in stack selection across visual styles, malformed recipe selectors and unknown/traversal-like names rejected before any provider calls. =/prompt/stack-catalogs= covers legacy catalogs without stacks, custom replacement profiles and invalid unused entries. =/prompt/application-stack-artifacts= checks API context at every application generation stage and exercises a complete presence-control bundle followed by missing and empty variants of every required artifact. The sentinel content deliberately proves only presence validation, not generated application behavior.

The install test renders the installed application recipe from =/tmp= and compares embedded versus explicitly loaded installed catalogs, including real YAML/HTMX/ORM symbols, GitLab dependency URLs and SQL deliverables. See [[file:c-application.org][the C application guide]] for the separate generated application's SQLite, configuration, HTTP and optional provider test requirements. No live generation, application compiler invocation, browser session or external database call is part of these default builder tests.

=make stack-tests= is an additional opt-in real-library conformance probe after initializing =deps/yaml-glib=, =deps/htmx-glib= and =deps/orm-glib=. It compiles against the pinned archives and checks YAML integer versus quoted-string typing, HTMX callback routing and escaping, SQLite first-file creation, parameter injection resistance, constraint failures, transaction commit/rollback and persistence after reopening. It neither generates an application nor opens an HTTP listener. It requires the generated C stack's SQLite build packages and leaves dependency build artifacts in their normal submodule build directories. This verifies the API subset supplied in prompts; it does not certify generated application's SQL, browser behavior or optional network databases.
