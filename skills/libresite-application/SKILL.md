# Generate an application with libresite

Locate the checkout or installed CLI and read `docs/recipe-format.org`, `docs/operations.org`, `docs/c-application.org` and `recipes/application.yaml`. Define a small complete user workflow before selecting modules. Preserve the requested stack. For C/GLib applications select `site.stack: c-glib`: yaml-glib runtime configuration, htmx-glib routing/HTML with local HTMX enhancement and ordinary form fallbacks, and orm-glib with SQLite by default. Optional PostgreSQL/MySQL providers need explicit build flags and matching bootstrap SQL. Visual style remains independent.

Write a new recipe describing routes, input constraints, state transitions, persistence and the actual audience. Use `application` style for repeated-use product interfaces. Choose a pipeline of brief, design, database, backend, frontend, review and native validate, adjusting order when a concrete integration requires it. Every step may specify its own `ai.provider` and `ai.model`. A changed provider should get its own model; inspect `--plan` before generation.

Treat mobile and desktop as first-class defaults without asking the user to opt in. Plan each route and workflow state for touch, keyboard and pointer, including navigation, forms, tables, dialogs and validation feedback; preserve all capabilities and deliberate desktop information density. Keep the shared responsive acceptance matrix from `docs/prompts.org` in generated test documentation and AGENTS.md: 360x800, 390x844, 768x1024, 1366x768 and 1440x900, intermediate widths, phone landscape and 200 percent zoom. Exercise the main workflow across this matrix when browser tooling is available, checking focus visibility, reflow and unintended overflow; label unexecuted checks honestly. Preserve these defaults when replacing the prompt catalog.

Carry the shared SEO defaults into every application recipe; read `docs/seo.org`. Require `config/seo.yaml`, `docs/seo.org` and `tests/seo.sh` in final native validation. Put supplied deployment URLs, language and public/private route requirements in `site.requirements`; do not invent recipe keys or domains. Local-only/private applications stay noindex and disclose no sitemap URLs, even if a base URL is supplied. Public pages need complete initial HTML, distinct metadata, consistent canonicals, truthful structured data, robots/sitemap routes and real error statuses, integrated with actual configuration and routing. Test full documents versus fragments on both loopback aliases; SEO settings must never weaken access controls. Inspect and execute generated SEO tests when authorized and feasible, document any remaining checks in README.org and AGENTS.md, and preserve defaults in replacement catalogs. A passing native text check does not certify SEO semantics or search outcomes.

Describe the frontend/backend/database contract explicitly in the brief. Do not replace persistence with an in-memory mock, invent an authentication flow, or choose a dependency that conflicts with the user's FOSS requirement. The embedded `c-glib` profile supplies verified library API context and pinned GitLab dependency setup without global installation; preview it before generation. When changing dependency versions or requesting additional APIs, inspect the real headers/docs and update the relevant contract. Keep projects small enough for the complete-context prompt limit. Use a native plugin or split genuinely independent components when a larger application cannot fit.

Preserve the shared accessibility and ARIA defaults from `docs/prompts.org` without requiring user opt-in, including in replacement catalogs. Require native semantics, valid names/roles/states and ID references, working keyboard patterns, focus handling and announcements in full-page responses, no-JavaScript forms and HTMX updates. Generated test documentation and AGENTS.md must provide runnable version-pinned FOSS browser accessibility audits covering routes and interactive states plus manual keyboard/screen-reader procedures with expected results. Run them when the runtime is available and repair findings; otherwise record unexecuted checks. Native validation and automated scans alone do not certify ARIA or accessibility conformance.

Preserve the application's required paths from `recipes/application.yaml`: dependency manifest/bootstrap script, YAML config and typed loader, main/pages/database sources, all three dialect bootstrap SQL files, configuration/database docs and tests. Adapt entities and routes to the brief without deleting these integration deliverables. SQL must match runtime migrations; SQLite starts without manual imports. Network credentials belong in environment variables named by YAML, never in generated files. Require strict config validation, unknown/disabled-provider failures, persistence after restart, parameter safety, rollback, schema parity and both full-page/HTMX form tests. An exported bundle has no gitlinks, so `.gitmodules` alone is insufficient dependency setup.

Require build files, README.org, AGENTS.md, product/design/review docs and concrete implementation files in the final native validation step. AGENTS.md is the maintenance file for later agents: exact commands, loopback URL aliases (127.0.0.1 and localhost), CSRF restart behavior, and how to diagnose form 403/422/503. A loopback application must accept Host/Origin for both 127.0.0.1 and localhost on the listening port; rejecting localhost is a product bug. Run `--validate`, inspect `--plan`, and preview the backend contract. Generate to a new directory with an installed/authenticated provider. Resume only matching work. Do not execute arbitrary generated setup commands without first reading them and confirming they fit the user's requested work.

After generation, inspect the output's README, AGENTS.md and build configuration. List the Fedora build dependencies explicitly. Run appropriate build/tests in the user's development environment; on an immutable host, do not mutate `/usr` or install host packages automatically. Exercise the main form workflow from both `http://127.0.0.1:PORT/` and `http://localhost:PORT/` if the runtime is available. A 403 that tells the user to "open the local address" after a same-browser loopback POST is a generator defect, not user error. A passing libresite `validate` step proves required non-whitespace text and configured content/size predicates; it does not prove a passing application build or browser test. Report actual checks, remaining runtime limitations and the output directory. Deployment remains a separate requested action.

Native validation can also enforce `options.checks`: exact artifact paths, case-sensitive `contains`/`excludes` literal lists and inclusive UTF-8 `min_bytes`/`max_bytes` integers. Use these for concrete source/documentation contracts while retaining `required`. Preflight rejects malformed predicates before generation; immediate downstream failures trigger corrective retries. These text checks do not prove that a backend builds or accepts HTTP requests.

Copy-lock approved client sentences and contact details using `validate.options.checks[].contains`; read `docs/copy-lock.org`. Apply literals to the exact source/template artifacts, with explicitly agreed escaping, and separately lock confirmed telephone destinations. Keep the final validator immediately after review for corrective retries. Preserve the lock in generated AGENTS.md and review rendered output and every repeated contact detail before delivery; source presence cannot prove visible or correctly functioning copy.
