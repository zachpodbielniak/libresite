# Generate a static site with libresite

Embed supplied client copy, logo SVG, brand YAML, approved legal text and binary identity assets in top-level `seed_artifacts`, a sequence of exact `path` / `content` mappings using YAML literal blocks. Binary seeds set `encoding: base64`. Read the seed contract in `docs/recipe-format.org`. These artifacts exist before the first step and appear in previews; no host file imports are supported. Use instructions and native checks when content must be preserved. Changing seeds invalidates a checkpoint; resume preserves accepted replacements.

Locate the libresite checkout or installed CLI. Read `docs/recipe-format.org` and `recipes/landing.yaml` from that checkout (installed copies are under `share/libresite`). Keep the user's audience, brand, supplied facts, assets, provider/model choices and output location authoritative.

Create a dedicated recipe rather than modifying the shipped example. Use the structured `site.pages`, `offers`, `contact`, `brand`, `copy_lock` and `languages` fields; read `docs/structured-recipes.org`. Preserve exact locked copy and supplied brand/contact facts. Keep audience, stack and accessibility requirements in `site`. Select `editorial`, `minimalist`, `industrial` or `cinematic` based on the brief. For sold work, start from the matching vertical recipe in docs/packages.org and preserve its full pipeline, fixed pages and acceptance predicates. The shared flagship-quality contract applies to every profile; landing.yaml is the complete studio SKU. The final native check should require the real output files, including the homepage, stylesheet, README, AGENTS.md and design/review documents. AGENTS.md tells a later agent how to preview, test and troubleshoot the generated site.

Treat mobile and desktop as first-class defaults without asking the user to opt in. Require deliberate phone, tablet and desktop compositions and complete navigation/content/actions on every route. Keep the shared responsive acceptance matrix from `docs/prompts.org` in generated test documentation and AGENTS.md: 360x800, 390x844, 768x1024, 1366x768 and 1440x900, intermediate widths, phone landscape and 200 percent zoom. After generation, check viewport configuration, reflow, media, touch/keyboard/pointer access and unintended overflow; label browser checks unexecuted when no browser evidence exists. Native validation proves required non-whitespace text and configured content/size predicates. Preserve these defaults when replacing the prompt catalog.

Carry the shared SEO defaults into every recipe; read `docs/seo.org`. Put any supplied real HTTPS deployment URL (including a subpath), language and privacy constraints in `site.requirements`, not invented recipe keys. With no supplied URL, retain a usable noindex preview without guessed canonical/social URLs or a public sitemap. Require `config/seo.yaml`, `docs/seo.org`, `tests/seo.sh`, `robots.txt` and `scripts/prepare-seo.sh` in the final native validator. Public preparation must produce a separate deployable directory with consistent per-route metadata, canonical URLs, truthful JSON-LD and sitemap/robots output, preserving private/error exclusions. Keep source HTML directly previewable. Inspect the generated preparation/tests before running them; report actual results and unexecuted HTTP/browser/social checks honestly. Native text checks cannot establish semantic SEO or rankings. Preserve the contract in replacement catalogs and include exact maintenance commands in README.org and AGENTS.md.

Specify a real destination for each conversion action. Do not invent contact information, customers, testimonials or statistics. A static site should not imply that a signup or payment backend exists. Use original SVG for illustrations when that is enough. Favicon, OG image, WebP/PNG and font files are first-class binary artifacts with `encoding: base64`. Responses may `delete` and `rename` files; omitted paths survive. Stage `options.files` focuses prompt contents so later pages are not resent in full.

Preserve the shared accessibility and ARIA defaults from `docs/prompts.org` without requiring user opt-in, including in replacement catalogs. Require native semantics, valid names/roles/states and ID references, working keyboard patterns, focus handling and announcements on every route and state. Generated test documentation and AGENTS.md must provide runnable version-pinned FOSS browser accessibility audits and manual keyboard/screen-reader procedures with expected results. Run them when the runtime is available and repair findings; otherwise record unexecuted checks. Native validation and automated scans alone do not certify ARIA or accessibility conformance.

Run the recipe through `--validate`, inspect `--plan`, and inspect `--preview design` (or `--preview plan` and `--preview pages` for a composed recipe) plus `--preview design-gate`. If the builder needs changes, read repository `AGENTS.md`; keep recipe work separate from tool implementation. Build with GNU make if necessary. Run generation with `--recipe FILE --output DIR` once the brief is concrete and the requested generation is authorized. Bundled recipes stop at `design-gate` with exit status 7, which means waiting for review, not failure; inspect `OUTPUT.libresite-work/review/design-gate/` and resume with `--approve design-gate`. Use `--approve-all` only for unattended runs. The output directory must be new and its parent must exist. A provider must be installed and authenticated; report an actual setup failure without inventing success.

Use `--resume` only with the same output, recipe and prompt catalog after an interruption. After publication, run `libresite --qa DIR` for structural HTML/asset checks. Native `validate` remains literal in-process and is not HTML/a11y/SEO/compile; add `shellcheck: true` to a `checks` rule for each emitted shell script so ShellCheck findings (static, never executed) return to the model for correction. Read the generated README and review document. Check the actual HTML, stylesheet, links and keyboard behavior, and use browser tooling if available. Distinguish what was checked from model claims. Report the generated directory and how to open it; do not deploy or publish it to a service unless requested.

For prompt changes, edit a copied full `data/prompts.yaml` catalog and use `--prompts FILE`. The snapshots in `data/design-references` are reference material; the centralized runtime catalog already reconciles their conflicting directions.

For explicit delivery contracts, add `validate.options.checks` with exact `path`, `contains`/`excludes` literal lists and optional inclusive `min_bytes`/`max_bytes` integers. Read `recipes/checked-landing.yaml` as an example. Keep `required` for files that must contain non-whitespace text. These predicates run before candidate acceptance and can trigger corrective retries; they do not replace browser or accessibility review.

To change a site built from components, read `docs/editing.org` and run `libresite --edit SITE --change "the change"`; it commits one new version per change on the site's own history and refuses uncommitted or out-of-band changes. Pass the owner's request in their words and add any facts it needs; never invent prices, hours or people. For an existing project that was not built from components, read `docs/revision.org` and use `--revise SOURCE -r CHANGE.yaml -o NEW-DIR`. Put the change brief in `site.brief`; start with `recipes/revision.yaml`, customize acceptance checks, and inspect `--revise SOURCE --preview revision`. Preserve existing design and unrelated behavior; new-project scaffolding requirements above apply only when requested by the change brief. Input is regular UTF-8 text and binary assets, excludes administrative metadata, and does not honor `.gitignore`; select a source-only directory with no local secrets. The source is preserved and the output is a fresh repository. Resume requires unchanged source files, executable intent, recipe and catalog.


Copy-lock client-supplied sentences by default: read `docs/copy-lock.org` and `recipes/copy-locked-landing.yaml`. Copy approved sentences verbatim into `validate.options.checks[].contains` on each intended page; lock confirmed telephone href literals separately. Merge checks for the same path and place validation immediately after the last generative stage, including review. Preserve exact case, punctuation and digits; resolve missing or conflicting contact facts with the client. Explain any necessary HTML escaping explicitly. Require visible placement and consistent repeated facts in the brief and generated AGENTS.md. Before delivery, inspect rendered copy, all contact occurrences, actual call destinations and production-prepared output; literal presence alone cannot establish those properties. Never substitute illustrative example contact details for client facts.

For a sold order, read `docs/packages.org`. Keep `package.sku`, `package.release` and `package.kind` aligned with the agreed fixed scope, replace illustrative facts with approved client inputs, and preserve final native checks plus `docs/acceptance.org`, `tests/check.sh` and `tests/accessibility.sh`. Preflight and seal before generation with `libresite -r client.yaml --seal-package ORDER-DIR`, then use `libresite --package ORDER-DIR -o OUTPUT` and the same command with `--resume`. Back up the package and checkpoint together. Do not edit an old sale or substitute the current catalog to resume; create a new sealed order for scope changes. Pin compatible generator/plugins separately. A seal proves input identity, not executed browser tests or visual quality.

## Native scaffold

Prefer the composed pipeline for new static sites: `{id: plan, type: plan, options: {sector: SECTOR}, instructions: ...}` with the business's sector (trades, food, community, advisory, software, creative, retail or wellness) so the builder deals a fitting palette, type pairing and home order, a `design-gate` reviewing `site/plan.json`, `{id: pages, type: pages, options: {parallel: 12}, instructions: ...}`, the final `validate` acceptance, then `{id: build-notes, type: prune, options: {prefixes: [site/], archive: true}}`, which keeps the plan and page outlines in the run record instead of the published site. Put per-page content requirements in the plan instructions and exact literals in acceptance `contains` checks; each page writer receives its own. It writes every page at once from the component library and ships the 404, privacy and terms pages itself, so it needs no scaffold step. See `docs/components.org` and `recipes/studio.yaml`. For the bundle pipeline, start with `{id: scaffold, type: scaffold, options: {profile: static}}` before AI stages. It supplies a 404 and privacy/terms draft shells without model calls. Existing paths are preserved; supply approved legal text through seeds. End static pipelines with `{id: build-notes, type: prune, options: {paths: [docs/product.org, docs/design.org]}}` after acceptance. A static site ships no README, AGENTS.md, Makefile, tests or scripts; do not require them in acceptance (see `docs/deliverables.org`). Do not enable a contact form without a real endpoint or turn draft legal shells into invented policies. Native `--preview scaffold` returns JSON; later CLI previews include the templates. See `docs/scaffold.org`. Do not add static scaffolding automatically to revisions or C application pipelines.
